## analysis agent (set list + auto mix round)

- analysis (src/analysis/bpm.js): `BeatInfo.beats` is a `Float64Array` (track seconds, increasing) from the first beat >= 0 to the end of the track, with `beats[0] === firstBeat`; `null` exactly when `bpm` is null. Steady tracks get the exact constant grid (`firstBeat + k * 60 / bpm`), so map- and grid-based code agree to the microsecond. Variable tracks get the tracked map: 16-beat local folds every 4 beats in the map's own coordinate (stage 7 in the file header), drumless intros / outros continued as a straight grid at the local tempo. For a variable track `bpm` is the average tempo over the tracked stretch (beats / time) and `firstBeat` is `beats[0]` (not the fold anchor). The map belongs to the detected tempo: when a deck replaces bpm/firstBeat (user x2, /2, TAP, `setBpm`, or the known demo values in `demoBeats`), it should drop the map (use the grid) instead of mixing the two.
- analysis: `variable` is now decided by the beat map when it covers >= 20 s and followed the beat in >= 75 % of the windows with music: the map's residuals from one straight grid, smoothed over +-8 beats, RMS > 6 ms or 95th percentile > 12 ms (a bending map must also line up the onsets better than the straight grid). The old Fourier-residual / per-beat-regression rule only decides when there is no usable map. Real-song regression (tests/realsongs.test.js): Boss Battle Groove 148.096, steady (3.3 ms RMS), confidence 1; Bubble Star Parade 140.29 (local 140.12 -> 140.51), Arcade Rush 141.52, Kaleidoscopic Loop 141.07 (140.50 -> 141.55), all variable, maps within ~2 ms (median) of an independent beat tracker's maps and of the kick onsets.
- analysis: confidence factor for variable tempo is 0.8 when the map follows the drift (contrast then measured in the map's coordinate), still 0.5 without a usable map; steady tracks unchanged.
- analysis (src/analysis/loudness.js): `gainDb` = -13 dBFS RMS target (90th percentile of 400 ms windows), capped so `peakDb + gainDb <= +2`, clamped -12..+6 (CONTRACT section 3 said -12 target, clamp -12..+9). Extra exports `TARGET_RMS_DB`, `PEAK_CEILING_DB`, `GAIN_MIN_DB`, `GAIN_MAX_DB`.
- analysis (src/analysis/analyze-worker.js): the result message transfers `beats.beats.buffer` (the map is not copied).
- analysis tests: `tests/beatmap.test.js` (synthetic: constant = grid, 0.5 % wobble and 120 -> 124 ramp within 10 ms of truth, drumless intros, humanize stays steady), `tests/realsongs.test.js` (your own WAV files in tests/media/, skipped with a `# SKIP` line when missing; ~25 s alone, ~45 s inside a full parallel `jscheck test tests`). Note for the reference values: the reference tracker's map of Arcade Rush has one extra beat in the fill + breakdown at 62-73 s (the kicks after it sit every 2 beats of a steady ~141.3 grid), so its "~141.9" average is ~0.4 high; the real average is ~141.5.
- analysis (refinement of the bullet above): a straight map proves a steady tempo when it followed the beat in >= 50 % of the windows with music (songs with long breakdowns); a bending map is used as the grid only from 75 %.

A map that starts after firstBeat counts its offset with its own local beat length (16-beat average), and extrapolation past either end uses that average too (robust to per-beat jitter of the map).
- sync (src/deck/sync.js): `setSync(index, on, { align: false })` skips the alignment jump (Auto Mix starts the slave on the beat itself). Exact alignment: both decks' `positionAt(t)` for t = audioTime + 0.1 s (0.05 s when a paused slave starts) and `slave.seekAt(target, t)`; decks without that API still jump at once. No alignment jump and no phase correction while either deck has a pending scheduled start/jump (`deck.scheduledAt`). Phase lock also for `variable` tracks when they have a beat map.
- deck-math (src/deck/deck-math.js): additive `beatPhase(pos, bpm, firstBeat, beats?)`, `loopBounds(..., map?)`, `doubleBeatMap`, `halveBeatMap`, and the tempo-ramp kinematics `rateAt`, `travelDistance`, `travelTime` (motion = { rate, bend, ramp: { c0, c1, r0, r1 } }).

- playlist (src/deck/playlist.js): additive `length`, `current`, `get(uid)`, `indexOf(uid)`, the `library` / `settings` properties, `setCurrent(-1 | null)` (none current: the first song is next); exports `itemRef(entry)`, `titleFromFileName(name)`, `MAX_SET_LIST` (200). `items` is a frozen array replaced on every change; items are frozen (a new object when their details change). Removing the current song makes the one before it current (so the next song stays next). An outside `settings.setList` change (Reset all settings) reloads the list.
- automix-plan (src/deck/automix-plan.js): Transition = `{ mode, multiplier, beats, fadeSec, out: { at, beat, beats }, in: { at, beat }, tempo: { mode, multiplier, nextStartRate, curTargetRate, meetBpm, preRampBeats, returnSeconds }, bassSwap, bassSwapBeat, echoOut, late, curBounds, nextBounds }`. `planTransition(cur, next, settings, opts)` takes a 4th `opts { earliest, noPreRamp }` (MIX NOW / missed mix point: first bar after `earliest`, `lateOutPoint`). For beat-matched mixes the in-point moves back to the start of its bar (up to 3 beats of the quiet intro play) so the next song's bars land on the current song's bars; a bar before the start of the file moves forward instead. Extra exports `lateOutPoint`, `returnSeconds`, the constants. `crossfadeAt(progress, from = -1, to = 1)`.
- automix (src/deck/automix.js): constructor also takes `library` (default `playlist.library`) and `deps` (timers, `hidden`) for tests; `dispose()`. Takeover detection listens to the mixer's 'crossfader' events with `source: 'user'` (and `noteUserCrossfader()`); 'restore' / 'auto' sources are ignored. `nextItem` for a song the user loaded on the prepared deck is `{ uid: null, kind: 'deck', id: null, title, artist }` (mixed into; the set list does not advance for it). 'change' carries 'enabled' | 'state' | 'plan' | 'next' | 'mix'. Behaviour details: the meet pre-ramp ENDS at least 4 beats and 2.6 s before the mix (not at t0), so the mix is put on the audio clock at a steady tempo; while the page is hidden the mix is scheduled 20 s ahead (timers may be throttled) without a pre-ramp. Before t0 a timing action by the user (play/pause/cue/seek/scratch/tempo/loop/bpm/load/eject) cancels the prepared mix (undoes the scheduled start, crossfade, EQ and a pre-ramp the user did not override) and re-plans instead of switching off; a user crossfader move after the mix was scheduled, or any user action during the mix, is a takeover. A cut transition from a song with a beat grid also uses Deck.echoOut.

## integrator (set list + Auto Mix round)

- automix (src/deck/automix-deck.js): `waitAnalysis(deck, ms, timers)` checks the deck state one microtask after each 'change' event. A real Deck emits its 'loading' change (track set, loading over) just BEFORE it starts the analysis, so a wait that began while the deck was still loading (a user loading their own song on the prepared deck) resolved before the BPM was known: that song was planned as a 'cut' and never re-parked. New helper `releaseNextDeck(deck, touched)`.
- automix (src/deck/automix.js): a session counts as mixing from t0 on the audio clock (`_mixing`), not only after the next 100 ms tick flips its phase. A user action in between is a takeover. Before, it re-planned and later restarted the already playing next song. Applies to user actions, switching off (freeze instead of undo) and 'ended'.
- automix: MIX NOW during the meet pre-ramp now stops the ramp at the rate it has reached (`rampTempo(rate, 0)`), as its comment said. Before, the ramp kept running under the mix while the next song started at the ramp's end tempo.
- automix: `_replan` returns whether it re-planned. A BPM that arrives or changes on either song always re-plans, also inside the 30 s freeze. After a re-plan from a deck change, a late or hidden-page re-plan, or a "too late for the pre-ramp" re-plan, the next deck is parked again (in-point, start tempo, bass cut) without moving the crossfader (`_park`). Before, a next song analysed after the 30 s wait kept its 'cut' plan and an unparked bass.
- automix: while the first song is starting, a load or eject on the other deck no longer stops the start (the loaded song simply becomes next). PLAY on the other deck makes that deck current, and the first song (already on deck A, never started) stays next and is reused, not loaded again. A user action on deck A marks the first song as current.
- automix: previewing the next deck (seek / play / cue) during the meet pre-ramp no longer cancels the session. Before, the current song glided back toward its old tempo for 3 s and then ramped again.
- automix: a user song still decoding after the 30 s wait is waited for again instead of being loaded over with the set list's song. `nextItem` for a user song is `{ uid: null, kind: 'deck', title: 'your song on deck B', ... }` while it loads, then its real title.
- automix: switching off, or emptying the rest of the set list, gives the parked (paused, untouched) next deck its bass back. The tick runs through `_safeTick`, which logs a failing tick once. The async steps (start, preload, next song) end in a `.catch` that logs.
- tests/automix.test.js: `realRig()` helper (real Decks, SyncController, Playlist, AutoMix on clock players). New tests: real-deck waitAnalysis, user song on the prepared deck end to end, meet + ease back + cut with echo out to the end of the set end to end, MIX NOW in the pre-ramp, previewing during the pre-ramp, a user action between t0 and the tick, a late BPM inside the freeze window, user actions while starting (load on B, PLAY on B), and bass released on switch-off / list emptied. `setup()` takes `deps`; the catalog has a `slow` song (analysis after 90 s).
