# research-engine
## Findings
- [medium,critical] For touch scratching, follow the finger's position with smoothing rather than only its velocity. Open-source examples differ. GalacTechNyc/djay (deck-core.js) computes gap = target - pos, converts it to a desired speed over a window of about 20 ms, and smooths per sample with rate += (want - rate) * 0.05, capped at +/-12x. Swipe strokes use a raised-cosine curve (0.5 - 0.5*cos(pi*x)) so velocity is zero at both ends. musudik/DJ-Console sets the rate directly from the jog value (rate = jog) with no smoothing and no declick. pixelputra-cloud/dj-scratch-deck uses an a-rate 'rate' AudioParam in the range -16..16, smoothed with setTargetAtTime. Velocity-only control drifts away from the finger and the platter. Position following keeps baby scratches anchored. Without smoothing, 60-120 Hz pointer updates make the velocity a step function, which buzzes at the event rate.
- [high] Reference smoothing constants from established DJ software. Mixxx jog scratching uses an alpha-beta filter with alpha = 1/8 and beta = alpha/32 per jog tick, at 33 1/3 RPM. xwax timecode tracking uses ALPHA = 1/512 and BETA = ALPHA/256 per audio sample. Mixxx switches to its linear scaler during scratching because SoundTouch/RubberBand lag on direction changes (PR #15845). After GSoC 2025 Mixxx offers libsamplerate tiers. Measured per-buffer cost: linear 10 us, fastest sinc 57 us, best sinc 448 us.
- [medium] Measured in Chrome 152 on a Windows desktop with 16 threads, during this research. Interpolation costs per output sample: linear 1.17 ns (Float32 source) / 1.62 ns (Int16 source); 4-point cubic Hermite (Catmull-Rom) 2.89 / 4.71 ns; 16-tap windowed sinc with a 256-phase table 19.5 / 26.2 ns at rate about 1. Two stereo decks at 48 kHz need 192k interpolations/s. That is about 0.55-0.9 ms of CPU per second for Hermite and about 3.8-5 ms for sinc16. A sinc kernel stretched for anti-aliasing at 4x scratch speed costs about 4x more. Assuming phones are 3-10x slower, Hermite stays under about 1% of one core, so interpolation is not the bottleneck.
- [high,critical] Over plain http://192.168.x.x the page is not a secure context, so AudioWorklet is unavailable. BaseAudioContext.audioWorklet is [SecureContext] in Web Audio 1.1 (W3C Working Draft, 22 Sep 2026) and on MDN, so ctx.audioWorklet is undefined there. HTTPS and localhost qualify. createScriptProcessor is not secure-context gated. It is deprecated ('may be a candidate for removal') but still present in Chrome, Firefox and Safari, with no removal milestone found.
- [medium] Support for static ES imports inside AudioWorklet modules: Chrome supports them; I verified in Chrome 152 that a blob module importing another blob URL loads. Firefox supports them only from 113 (bug 1572644; before that, 'Module resolve hook not set'). For Safari I found no authoritative evidence either way. Ship the worklet as one self-contained file with no imports.
- [medium,critical] addModule with a blob: URL works in Chrome 152 (verified here, including the new Blob(['(' + fn + ')()']) pattern). WebKit fixed fetching worklet modules from data: URLs in changeset 270046. A Content-Security-Policy whose script-src lacks blob: blocks blob worklets in Chromium and Firefox. Worklet modules are fetched in CORS mode. In a sandboxed iframe without allow-same-origin the origin is opaque, so even a same-host worklet file needs Access-Control-Allow-Origin. GitHub Pages sends 'Access-Control-Allow-Origin: *' (verified with curl on a github.io page).
- [high,critical] A source AudioWorkletNode created with numberOfInputs: 0 and no outputChannelCount renders MONO. Verified in Chrome 152: outputs[0].length was 1, and 2 when outputChannelCount: [2] was set.
- [medium,critical] node.port.postMessage(f32, [f32.buffer]) moves data to the worklet without copying. In Chrome 152, a 2.88M-sample Float32Array went in and the reply came back in about 0.1 ms. Transferring AudioBuffer.getChannelData(c).buffer also works in Chrome 152 (verified): the receiver gets the data, and the AudioBuffer's channel becomes detached (getChannelData returns length 0). Safari and Firefox behaviour for that AudioBuffer transfer is unverified. Without a transfer list the payload is structured-clone copied and deserialized on the audio thread. Heavy loops in the worklet's onmessage are reported to fail silently or glitch.
- [high] SharedArrayBuffer is not practical for this app. It needs a secure context plus COOP/COEP cross-origin isolation. GitHub Pages cannot set custom headers: community discussion #13309 has had no ETA since July 2023 and was still open in August 2026. The coi-serviceworker hack needs an extra reload and is reported unreliable. Safari does not support COEP: credentialless, so isolation there requires require-corp. A sandboxed iframe preview will not be crossOriginIsolated. postMessage at 30-60 Hz is enough for playhead reporting.
- [high] Latency APIs. outputLatency: Chrome 102, Firefox 70, Safari/iOS 18.4. baseLatency: Chrome 58, Firefox 70, Safari 14.1, iOS 14.5. getOutputTimestamp: Chrome 57, Firefox 70, Safari 14.1, iOS 14.5. In WebKit, baseLatency = framesPerBuffer / sampleRate. outputLatency returns 0 while not playing, and a fixed 512/sampleRate when fingerprinting noise-injection is on. Measured on Chrome 152 Windows: baseLatency 0.01 s; outputLatency 0 before playback. Bluetooth adds roughly 0.15-0.25 s (one measurement: 0.178 s, BT headphones, Firefox macOS).
- [high] WebKit ignores latencyHint: AudioContext.cpp has '// FIXME: Figure out where latencyHint should go.' Whenever Web Audio is active, WebKit asks for a hardware buffer of renderQuantumSize, which is 128 frames (MediaSessionManagerCocoa updateSessionState). Changing latencyHint on iOS therefore does nothing. In Chrome, 'interactive' is the lowest-latency default and 'balanced' or 'playback' give larger buffers.
- [high,critical] iOS silent switch: by default WebKit puts Web Audio in the AmbientSound category (MediaSessionManagerCocoa), which the ring/silent switch mutes. Setting navigator.audioSession.type = 'playback' moves it to the playback category, which ignores the switch. Apple's jya documented this on WebKit bug 237322 as available 'beginning with iOS 17'. caniuse lists navigator.audioSession from Safari/iOS 16.4 and Firefox 160; Chrome does not support it. The W3C Audio Session draft is dated 13 Nov 2024. 'playback' does not mix with other apps' audio, so it stops Spotify and similar.
- [medium] iOS background/lock: without 'playback', the AudioContext is suspended or interrupted when the page is backgrounded or the screen locks. WebKit bug 261554 ('AudioContext is getting suspended when page goes in the background even if navigator.audioSession.type is set to playback') was fixed in WebKit in March 2024 and confirmed in iOS 17.5. It regressed in 17.2-17.3. With type 'playback' on iOS >= 17.5, audio should keep running when locked. Device verification is still advised.
- [high] The 'interrupted' AudioContextState is in the Web Audio 1.1 WD. WebKit exposes it after calls, Siri, app switches and similar events, and resume() rejects or stays interrupted until the interruption ends. Chrome shipped it in 136 (desktop, Android, WebView), triggered by exclusive audio access or laptop lid close; Chromestatus says all platforms except iOS. Some iOS devices are reported stuck on 'interrupted' (web-audio-api issue #2585, open, no resolution).
- [high] Screen Wake Lock: Chrome 85 desktop (84 Android), Firefox 126, Safari and iOS 16.4 in browser tabs. iOS/iPadOS Home Screen web apps were broken from 16.4 to 18.3 (WebKit bug 254545) and fixed in 18.4.
- [low] Android Chrome with the screen off: I found no deliberate WebAudio suspension in a foreground tab. Web Audio alone gets no media notification, which needs a media element of at least about 5 s. OEM battery managers or Doze can kill a backgrounded browser after minutes (reports mostly from WebView/Capacitor apps). The main mitigation is to keep the screen on with Wake Lock while performing. Optionally play a silent looping <audio> element and set Media Session metadata.
- [high,critical] decodeAudioData output is resampled to the context's sample rate, and the input ArrayBuffer is detached (Web Audio 1.1 decodeAudioData steps). Decoded memory is therefore set by ctx.sampleRate, usually 48000 on phones. A 6 min stereo track takes 127.0 MB as float32 at 44.1 kHz or 138.2 MB at 48 kHz, and half that as Int16 (63.5 / 69.1 MB).
- [medium,critical] Memory risk on phones. The iOS Safari tab budget depends on device and uptime: reports of about 1.5-3 GB on iPhone 12 Pro/15 Pro and much less on low-RAM devices, and over budget the tab is silently reloaded. Older reports show Chrome decodeAudioData using huge peak memory on long files (one report: 73 MB podcast, 1.9 GB RAM). Decoding is also slow on Android, and a 9 MB MP3 crashed iOS Safari on an older device. Peak memory during load is roughly the encoded file plus the AudioBuffer plus any copy.
- [medium,critical] decodeAudioData format matrix, 2025-2026. MP3: all browsers. AAC/M4A: Chrome desktop/Android and Safari; Firefox through OS decoders. ALAC: Safari only. FLAC: Chrome 56+, Firefox 51+, Safari 11+ (iOS 11+, full macOS 13+). WAV PCM 16/24-bit and 32-bit float: Chrome and Safari (FFmpeg/CoreAudio); Firefox 24-bit/float support is likely but unverified. AIFF: Safari only (CoreAudio); Chrome and Firefox no. Ogg Vorbis/Opus: Chrome and Firefox. Safari 18.4 (iOS 18.4/macOS 15.4) added the Ogg container for media elements. WebKit's AudioFileReaderCocoa maps 'Oggf' to audio/ogg through AVFoundation, so decodeAudioData Ogg on iOS 18.4+ is likely but unverified. WebM Opus/Vorbis decodeAudioData in Safari: fixed 2021 (Safari 15 era). Opus-in-MP4 decodeAudioData in Safari: fixed in Safari 27.0. CAF Opus: Safari only.
- [high] WebCodecs AudioDecoder is available in Chrome 94+ and Safari 26.0+ (Safari 16.4-18.x had video-only WebCodecs). It is a possible fallback decoder but needs your own demuxer.
- [medium] iOS sample-rate pitfalls: the hardware usually runs at 48 kHz. Older iOS versions (9-14) had distortion when the AudioContext rate did not match the hardware, reportedly fixed by iOS 15. Do not force sampleRate in the constructor; read ctx.sampleRate and the worklet's global sampleRate. Safari 26.0 fixed 'stale audio buffer data after seeking when playing sound through an AudioContext'.
- [high] New Chrome Web Audio knobs. renderSizeHint (configurable render quantum) is on by default from Chrome 153 on desktop, Android and WebView; 'hardware' currently always returns 128. AudioContext.playbackStats (formerly playoutStats) is only a developer trial behind a flag from M146. AudioContext.onerror shipped in Chrome 128, desktop only. Web Audio Render Capacity API is still in development.
- [high] Node CPU costs. BiquadFilter costs about 5 multiplies and 4 adds per sample, so 6-8 biquads per deck are negligible in native code. In Chrome, a-rate automation (setTargetAtTime and similar) recomputes the biquad coefficients every sample; automationRate = 'k-rate' avoids that (Chrome 68+, Safari/iOS 14+, not Firefox). ConvolverNode is the most expensive node: cost grows with IR length, it copies the IR, and it can burst. DynamicsCompressor costs moderate CPU and adds a fixed 6 ms look-ahead. DelayNode is cheap. Per spec, a DelayNode inside a feedback cycle is clamped to at least one render quantum: 128 frames, 2.67 ms at 48 kHz.
- [medium,critical] Adjacent to scope, but it affects the 'one AudioContext' plan and the key requirement. Per caniuse: HTMLMediaElement.setSinkId is in Chrome desktop 49+, Firefox 116+, Safari/iOS 18.4+, and not in Chrome Android, Firefox Android or Samsung Internet. AudioContext.setSinkId is in Chrome 110+ (BCD also lists Chrome Android 154 and Samsung Internet 21+) and not in Safari or Firefox. To send master and cue to two devices from one engine you would need a second path, such as a MediaStreamAudioDestinationNode feeding an <audio> element with setSinkId. Phones may not expose or allow two simultaneous Bluetooth sinks. The fallback that works everywhere is split-mono: master on L, cue on R.
## Recommendations
- AudioContext: new AudioContext({ latencyHint: 'interactive' }). Do not pass sampleRate. Read ctx.sampleRate (typically 48000 on phones) and use the worklet's global sampleRate. Add a 'Stable audio' setting that recreates the context with latencyHint 'balanced' (or 0.04) on Chrome; it has no effect on Safari. Log ctx.baseLatency and ctx.outputLatency (once playing) to a diagnostics panel.
- Engine: one AudioWorkletProcessor per deck, created with numberOfInputs: 0, numberOfOutputs: 1, outputChannelCount: [2]. The processor owns the PCM, a float64 read head 'pos' in samples, 'rate', and the motor/hand state. Use outputs[0][0].length for the block size, never a hard-coded 128 (Chrome 153 renderSizeHint). Return true from process(). Allocate nothing inside process().
- Interpolation: 4-point cubic Hermite (Catmull-Rom) with c0 = p1, c1 = 0.5*(p2-p0), c2 = p0 - 2.5*p1 + 2*p2 - 0.5*p3, c3 = 0.5*(p3-p0) + 1.5*(p1-p2), y = ((c3*t + c2)*t + c1)*t + c0. Read samples outside [0, len) as 0 so reverse past the start produces silence, not a clamped click. Skip sinc. Linear is acceptable only for the ScriptProcessor fallback on very weak devices.
- Scratch input from the main thread: on pointerdown on the platter, call setPointerCapture, set CSS touch-action: none, and send {type:'grab'}. On each pointermove (use getCoalescedEvents() when available), unwrap the angle delta and compute targetPos = grabPos + (accumAngle/(2*PI)) * 1.8 * sampleRate. One revolution is 1.8 s at 33 1/3 RPM; use 1.333 s for 45 RPM. Post {type:'target', pos: targetPos (float64), t: performance.now()}. On pointerup send {type:'release'}. Never pass absolute positions through an AudioParam: AudioParam values are float32, and 2^24 = 16.78M samples is only 5.8 min at 48 kHz.
- Worklet scratch follower, run per sample while the hand is on the platter. Estimate targetVel from the last two target messages in samples per sample and clamp it to +/-12. Extrapolate targetPred = target + targetVel*framesSinceMsg for at most 30 ms, then hold. err = targetPred - pos. desired = targetVel + err/(0.012*sr), which is a 12 ms position time constant. rate += (desired - rate) * kS with kS = 1 - exp(-1/(0.004*sr)), about 0.0052 at 48 kHz (a 4 ms smoother). Clamp rate to [-12, 12]. If |err| > 0.25*sr, do a declicked jump instead. Alternative: an alpha-beta filter on message arrival at 60-120 Hz with alpha about 0.5 and beta about 0.1, then the same per-sample rate smoother.
- Motor model: on release while playing, ramp rate toward pitchRate with tau 60-80 ms. Play from stop ('vinyl start') ramps 0 to pitchRate over 100-250 ms. Stop ('brake') ramps pitchRate to 0 over 400-800 ms. Offer an 'instant' option that uses a 3-5 ms gain ramp instead. Use pitch fader ranges of +/-8% and +/-16%. Final rate = pitchRate (1 + pitch) times bufferRate/ctxRate (normally 1, because decode resamples to the context rate).
- Declicking: crossfade every discontinuous jump (hot cue, seek, loop wrap, beat-jump, sync phase snap) over 256 frames (5.3 ms at 48 kHz). Keep a second read head, linear-crossfade for loops and equal-power for unrelated material. Prefer phase sync by nudging (rate +/-2-4% for 0.3-0.8 s) over hard jumps. End of track: 5 ms fade, then stop.
- Playhead reporting: post from the worklet every 8 render quanta (1024 frames, about 21 ms, about 47 Hz) with {pos, rate, frame: currentFrame}. Avoid posting every quantum. On the main thread, in requestAnimationFrame, compute ts = ctx.getOutputTimestamp(), ctxNow = ts.contextTime + (performance.now() - ts.performanceTime)/1000, displayPos = msg.pos + msg.rate*(ctxNow*sr - msg.frame) - userVisualOffset*sr. While the finger is down, draw the platter from the finger angle (zero latency), not from audio. Expose a manual 'Bluetooth delay' slider of 0-400 ms for visuals and cue alignment.
- Loading worklets: build the worklet from a function in a normal ES module, with url = URL.createObjectURL(new Blob(['(' + workletMain.toString() + ')()'], {type:'text/javascript'})), then await ctx.audioWorklet.addModule(url). This avoids network fetches, CORS from opaque sandbox origins and import support differences. If that throws (strict CSP), fall back to addModule(new URL('./deck-worklet.js', import.meta.url)). Keep the worklet free of import statements. Put the DSP core in a plain class inside the same function so the ScriptProcessor fallback can reuse it.
- Fallback: if !ctx.audioWorklet (http LAN dev, very old Safari) or addModule fails, use ctx.createScriptProcessor(2048 on mobile, 1024 on desktop, 0 inputs, 2 outputs) running the same DSP core on the main thread. It must be connected to the destination to fire. For phone testing, use HTTPS (GitHub Pages deploy or an https tunnel) or chrome://flags/#unsafely-treat-insecure-origin-as-secure on Android Chrome. iOS has no such flag.
- Loading a track: (1) Release the deck's old buffer first by posting {type:'unload'} and dropping all references. (2) Read file.arrayBuffer() and await ctx.decodeAudioData(ab); the input is detached. (3) For each channel, try node.port.postMessage({type:'load', ch: [d0, d1]}, [d0.buffer, d1.buffer]) with d = audioBuffer.getChannelData(c). This is zero-copy in Chrome 152; in a try/catch fall back to d.slice() and transfer the copy. (4) Drop the AudioBuffer. Store Int16 to halve memory: convert in 1-second chunks on the main thread, yielding between chunks, then transfer the Int16Array buffers; the worklet multiplies by 1/32768. Precompute the waveform overview (peaks at about 150 points/s) before dropping the float data.
- Memory limits: warn above about 12 min per track on phones; at 48 kHz stereo a 12 min track is 276 MB as float32 or 138 MB as Int16. Never keep more than one PCM copy per deck. Never send a non-transferred (cloned) large buffer to the worklet. Show a decode progress spinner; decodeAudioData can take seconds on Android.
- File input: <input type=file accept='audio/*,.mp3,.m4a,.aac,.wav,.flac,.ogg,.oga,.opus,.webm,.aif,.aiff,.caf'>. Try decodeAudioData and show 'format not supported on this browser' on rejection. Do not pre-filter with canPlayType, because Safari's canPlayType and decodeAudioData disagreed historically. Note for users that the iOS picker only shows Files-app content, not the Apple Music library.
- iOS unlock sequence, in a non-passive pointerup/click/touchend handler (not touchstart): first set navigator.audioSession.type = 'playback' when 'audioSession' in navigator, then create or resume the AudioContext, then start the silent keep-alive <audio> (looping 1 s silent WAV blob, playsinline) in the same gesture before any await. Keep the keep-alive only on iOS < 17 or when audioSession is missing, and pause it when nothing is playing.
- Lifecycle: ctx.onstatechange plus a visibilitychange handler plus a one-shot pointerup listener. If state is 'suspended' or 'interrupted' and the user expects playback, call ctx.resume() and show a 'Tap to resume audio' overlay until state === 'running'. Never call close(). Also listen to navigator.audioSession.onstatechange on Safari.
- Wake lock: while the app is open with a deck loaded, call navigator.wakeLock.request('screen') and re-request on visibilitychange to 'visible'. In a cross-origin or sandboxed iframe it needs allow='screen-wake-lock'; treat failure as non-fatal.
- Mixer/FX graph per deck: worklet, then trim Gain, then a 3-band isolator from Linkwitz-Riley crossovers (2 cascaded 2nd-order Butterworth LP/HP per split at about 250 Hz and 2.5 kHz; 6-8 biquads) with per-band Gains (kill = 0), then a filter knob (one biquad, LP to the left / HP to the right, Q 0.7-1.0, 20 Hz-20 kHz exponential mapping), then FX sends, then channel fader Gain, then crossfader Gain, then master. Set automationRate = 'k-rate' (in try/catch) on biquad frequency/Q/gain. Smooth knob moves with setTargetAtTime(v, now, 0.015).
- FX parameters. Echo: DelayNode (maxDelayTime 2 s) with delayTime = 60/BPM * (3/4, 1/2 or 1), a feedback Gain of 0.35-0.5, and a lowpass biquad of 3-5 kHz in the loop. Flanger: base delay 3-5 ms (feedback loops cannot go below 2.67 ms), depth 1-3 ms from an OscillatorNode at 0.1-0.5 Hz into delayTime, feedback 0.5-0.7, 50% mix. Implement bitcrush (bits 4-8, sample-hold 2-8x) inside the deck worklet. Reverb: use ONE shared ConvolverNode send on an FX bus with a generated 1.5-2.5 s stereo noise-times-exponential-decay IR, not one per deck. Disconnect FX chains when they are off, with a 10 ms wet fade.
- Master limiter: DynamicsCompressorNode with threshold -2 dB, knee 0, ratio 20, attack 0.002, release 0.15. It adds a 6 ms look-ahead. Use one on the master bus only, and optionally one on the cue bus.
- BPM sync in the engine: tempo sync sets slave pitchRate = masterBPM*masterRate/slaveBPM. Phase sync computes the beat-phase difference from the beat grids at the current playhead positions and corrects with a timed nudge, using the hard 256-frame crossfaded jump only when the correction exceeds 1/4 beat.
- Cue/headphone architecture: render master and cue mixes in the same AudioContext as two separate buses so the deck worklets are shared. Offer three output modes, chosen by feature detection: (a) split-mono on one device (master mono to L, cue mono to R, with a ChannelMergerNode); (b) cue bus into a MediaStreamAudioDestinationNode, then <audio>.srcObject with audio.setSinkId(id) where supported (desktop Chrome/Firefox, Safari 18.4+); (c) desktop Chrome only, ctx.setSinkId for master. Phones may not offer two simultaneous Bluetooth outputs; verify on device.
## Gotchas
- A source AudioWorkletNode without outputChannelCount: [2] outputs mono (verified in Chrome 152).
- Safari ignores latencyHint completely (WebKit FIXME). Do not expect 'interactive' or 'playback' to change anything on iOS.
- Over http://<LAN-IP>, ctx.audioWorklet is undefined in Chrome, Firefox and Safari, so you must use the fallback or HTTPS when testing on a phone.
- Static import inside a worklet throws on Firefox < 113 and is unverified on Safari. Ship one self-contained worklet script.
- A blob: worklet URL is blocked if the host page's CSP script-src lacks blob:. A sandboxed iframe without allow-same-origin makes even same-host worklet/module fetches CORS requests, which works on GitHub Pages because it sends ACAO: *.
- AudioParam values are float32, which cannot represent sample positions beyond 2^24 = 16.78M (5.8 min at 48 kHz) exactly. Send positions as float64 via port messages, and use AudioParams only for rates and gains.
- A large structured-clone (non-transferred) postMessage to a worklet deserializes on the audio thread and causes dropouts. Always use a transfer list, and keep onmessage handlers O(1).
- Transferring AudioBuffer channel buffers detaches them: the AudioBuffer becomes unusable (getChannelData returns length 0 in Chrome). Extract the waveform first. Behaviour on Safari and Firefox is unverified, so use try/catch with a copy fallback.
- decodeAudioData resamples to the context rate (memory scales with ctx.sampleRate) and detaches the input ArrayBuffer. Slice the ArrayBuffer first if you need it again, for example to retry.
- Old iOS versions silently reload the tab when over the memory budget, with no catchable error. Two 10-minute float32 decks at 48 kHz already use about 460 MB.
- Only pointerup, touchend, click and keydown reliably unlock audio on iOS; touchstart does not count. Set navigator.audioSession.type before starting audio. 'playback' stops other apps' music.
- An iOS context can sit in 'interrupted' after calls, Siri or locking, and resume() rejects until the interruption ends. Retry on visibilitychange and the next tap, and show a resume overlay.
- With 'playback', iOS background audio works from 17.5 (WebKit 261554); it regressed in 17.2-17.3. On older iOS, keep a silent <audio> element playing.
- Wake Lock in iOS Home Screen web apps only works from iOS 18.4. It is released when the page is hidden and must be re-requested. In a cross-origin iframe it needs allow='screen-wake-lock'.
- A DelayNode in a feedback loop is clamped to at least one render quantum: 2.67 ms at 48 kHz, or more if the render size changes. This limits feedback flangers built from native nodes.
- In Chrome, setTargetAtTime on biquad.frequency computes coefficients per sample unless automationRate is 'k-rate'. Firefox lacks automationRate, so guard the assignment.
- ScriptProcessorNode runs on the main thread, so canvas or waveform drawing jank causes audio dropouts. Use buffer sizes of 2048-4096 on phones, and it only fires while connected to the destination.
- Bluetooth outputLatency is often 0.15-0.25 s. Scratching over Bluetooth will feel late. Draw the platter from the finger, not from audio, and consider a latency-calibration slider.
- Do not trust canPlayType to predict decodeAudioData on Safari; there were historical mismatches for WebM Opus. Just attempt the decode and handle the rejection.
- WebKit returns outputLatency = 0 while the context is not playing, and a fixed 512/sampleRate under fingerprinting protection. Read it after playback starts, and re-read it periodically (route changes).
- Many recent GitHub DJ/worklet repos found in search look AI-generated. Use them as idea references only, not as authoritative behavior data.
