# research-synology
## Verdict
TwinSpin can play NAS music, but it cannot call the Synology DSM API directly. DSM's /webapi sends no Access-Control-Allow-Origin header, and DSM 7.2 to 7.4 has no CORS setting. The Login Portal reverse-proxy "Custom Header" adds request headers, not response headers. So a page on ranama.github.io cannot read login, list or download responses from the NAS unless the NAS gets an extra front door that adds CORS. Two routes work reliably. (1) Zero code, works today: make the NAS appear in the phone's or laptop's own file picker, then use TwinSpin's existing "Add music" button. Use SMB in the iPhone Files app, the Synology Drive app (Files app integration, and it works away from home through QuickConnect), CIFS Documents Provider on Android, or a mapped network drive on a laptop. (2) Best in-app integration: run Navidrome, a Subsonic-compatible music server, on the NAS. Its source sends Access-Control-Allow-Origin: * on every route; I checked this in the source on 2026-10-16. Put it behind a DSM reverse proxy using a *.synology.me DDNS name with a Let's Encrypt certificate, then build a Subsonic/OpenSubsonic client in TwinSpin. A native DSM File Station connector is possible only with a self-installed CORS proxy (Docker Caddy, a custom nginx file over SSH, or a Web Station PHP bridge). It is less reliable: DSM updates, the CSRF/Origin fix in DSM 7.2.2, IP-bound sessions and 2FA all get in the way. Do not build these, because they do not work: direct DSM calls, QuickConnect from the browser, the WebDAV Server package, share links, or http://LAN-IP from iPhone.
## Recommendation
Ranked by reliability:
1) ZERO-CODE FALLBACK (ship now as an in-app help card titled 'Add music from your NAS'; works on every device today): iPhone at home → Files app > Connect to Server > smb://<NAS-IP>, then TwinSpin Add music > Browse > Shared > NAS. iPhone away → Synology Drive app (signs in through QuickConnect) with the music share enabled as a Drive Team Folder, then pick from the 'Synology Drive' location. Android → CIFS Documents Provider with an SMB connection, then pick from the system chooser. Laptop → map \\NAS\music (Windows) or connect to smb://nas/music (macOS) and pick files. Optional small code: an 'Add folder' button (input webkitdirectory) and, on Chrome/Edge desktop, showDirectoryPicker() with the handle saved in IndexedDB for a rescannable 'linked NAS folder'.
2) BUILD: a 'Music server' source speaking Subsonic/OpenSubsonic, aimed at Navidrome on the NAS. It is the most reliable in-app integration because CORS comes from Navidrome itself and DSM updates can't break it. User configuration: (a) install Container Manager and create a Navidrome project (deluan/navidrome, 4533, /volume1/music:/music:ro, a non-admin uid); (b) DDNS <name>.synology.me with 'Get a certificate from Let's Encrypt'; (c) a Login Portal reverse proxy from https://music.<name>.synology.me:443 to http://localhost:4533 using that certificate; (d) router forward of 443 (and 80 for renewal), or Tailscale serve instead of port forwarding; (e) a Navidrome user plus an API key. TwinSpin design: connect sheet (URL + API key, or user/password turned into md5 token+salt), ping test, browse Artists/Albums/Playlists/Search, and per song either 'Import to library' (download.view → arrayBuffer → decodeAudioData → Blob in IndexedDB, tagged {source:'subsonic', server, id}) or 'Load to deck' (fetch and decode without storing). Use stream.view?format=mp3&maxBitRate=320 for formats the device can't decode. Allow 1 or 2 downloads at a time on phones, with AbortController and progress. Show clear diagnostics for http:// URLs (mixed content), a blocked Local Network Access permission, and TypeError fetch failures (certificate, CORS or offline).
3) OPTIONAL, LATER: a 'Synology DSM (File Station)' source, only for users who install a CORS front door: Caddy container (C1, preferred), SSH nginx sites-enabled file (C2, re-check after DSM updates), or a Web Station PHP bridge (C3). Use format=sid with _sid and SynoToken query parameters, a POST form-urlencoded login, OTP plus device token (store did), and silent re-login on errors 106/107/119/150. The front door must strip Origin/Referer and allow only https://ranama.github.io and http://localhost:8100. Audio Station browsing and transcoding (D) can sit on top, but it is undocumented.
4) DO NOT BUILD: direct DSM calls without a proxy, QuickConnect from the browser, the WebDAV Server package, public share links, http://LAN-IP (it never works on iPhone).
SECURITY (any connector): create a dedicated read-only account (DSM user 'twinspin' with Read-only on the music share, No access elsewhere, File Station or Audio Station privileges only; or a non-admin Navidrome user). Prefer API keys or tokens over passwords. Keep the DSM sid in memory or sessionStorage only, with did in localStorage; store a password only on explicit opt-in. Expose only the music service hostname to the internet, never DSM's 5000/5001. Keep DSM Auto block and 2FA on, and DSM at 7.2.2-72806 or later. Restrict any CORS front door to TwinSpin's exact origins, not *, and without credentials.
### A. Zero-code: NAS in the OS file picker, then TwinSpin's existing 'Add music' input (RECOMMENDED FALLBACK, ship as help text now)
- **howItWorks**: The OS mounts or exposes the NAS share. TwinSpin's existing <input type=file multiple accept=ACCEPT> (src/ui/dom.js fileLabel, ACCEPT in src/audio/decode.js) opens the system document picker, which already lists those locations. The picked files come in as File objects and are copied into the IndexedDB library as today. No network code, so no CORS, mixed-content, certificate or Local Network Access issues.
- **userSetup**: NAS: Control Panel > File Services > SMB: enable, set max protocol SMB3 (min SMB2; the iOS Files app needs SMB2+). Create a user with read access to the music shared folder. IPHONE AT HOME: Files app > Browse > ... > Connect to Server > smb://<NAS-LAN-IP> > Registered User > log in. The share appears under 'Shared'. In TwinSpin tap Add music > Choose File/Browse > Shared > NAS, then 'Select' to pick several files. IPHONE AWAY: on the NAS install Synology Drive Server and enable the music shared folder as a Team Folder (Synology Drive Admin Console > Team Folder > Enable). On the iPhone install the Synology Drive app and sign in with the QuickConnect ID. Its folders, including Team Folders, appear as a 'Synology Drive' location in Files and in Safari's picker. Alternatively install Tailscale on the NAS and the phone and use smb://<100.x Tailscale IP>. ANDROID: install CIFS Documents Provider (F-Droid or Play, v2.4.0, Oct 2025) and add an SMB connection to the NAS IP and share. Then TwinSpin Add music > system picker > menu > the CIFS share. LAPTOP: Windows Explorer > Map network drive \\<nas>\music, or macOS Finder > Go > Connect to Server smb://<nas>/music. Then pick files in TwinSpin.
- **browserConstraints**: None of the cross-origin rules apply because files arrive as local File objects. iOS copies each picked file from SMB or the File Provider into a temp location before Safari gets it, so large multi-selects are slow over Wi-Fi. Android SAF providers may be slow, and the CIFS app warns that some apps crash when streaming from it, but a one-shot file read is fine. Works in iPhone Safari, Android Chrome and desktop Chrome/Edge/Safari/Firefox. Away from home it needs Tailscale or the Drive app; plain SMB should never be port-forwarded.
- **apiDetails**: No new code needed. Optional small upgrades: (1) an 'Add folder' button using <input type=file webkitdirectory> (desktop browsers) to bulk-import a mapped NAS folder; (2) on Chrome/Edge desktop, window.showDirectoryPicker() with the FileSystemDirectoryHandle stored in IndexedDB as a 'linked NAS folder' that can be rescanned. This needs handle.requestPermission({mode:'read'}) once per session after a user gesture. It is not available in Safari or Firefox, and Android support is uncertain.
- **pros**: Works today with zero TwinSpin changes. Most reliable option on every device and immune to CORS, certificates and DSM updates. No credentials stored in the browser. Uses DSM's own SMB permissions. The Drive app reaches the NAS away from home through QuickConnect (a native app, so the browser limits don't apply). Imported songs stay offline in IndexedDB, which suits DJ sets.
- **cons**: No browsing of the NAS library inside TwinSpin; the user navigates folders in the OS picker. Files are copied, not linked (except the showDirectoryPicker option on desktop Chrome/Edge). Android needs a third-party app. The Synology Drive route needs Drive Server and a Team Folder. It is not yet verified on a device that Safari's file input lists SMB and Synology Drive locations; it uses the same UIDocumentPicker, so it is very likely, but test it.

### B. Navidrome (Subsonic/OpenSubsonic server) on the NAS + TwinSpin 'Music server' connector (RECOMMENDED BUILD)
- **howItWorks**: Navidrome runs in Synology Container Manager, indexes the music shared folder (read-only mount) and serves the Subsonic REST API. Its chi middleware sets CORS AllowedOrigins ['*'], AllowedHeaders ['*'] and AllowCredentials false on all routes (server/middlewares.go corsHandler, checked on master 2026-10-16). TwinSpin can therefore fetch() JSON and audio bytes cross-origin. DSM's reverse proxy provides HTTPS with a Let's Encrypt certificate on a synology.me DDNS name. TwinSpin browses artists, albums and search, then download.view → arrayBuffer → decodeAudioData → Blob into IndexedDB (or loads straight onto a deck).
- **userSetup**: 1) Package Center: install Container Manager (DSM 7.2+). x86 Plus models have it; DS223, DS420j, DS220j and DS120j got ARMv8 support per the release notes. Check your model. 2) File Station: create /docker/navidrome. 3) Container Manager > Project > Create with this compose: image deluan/navidrome:latest; ports '4533:4533'; volumes /volume1/docker/navidrome:/data and /volume1/music:/music:ro; user: '<uid>:<gid>' of a non-admin user with read access to music; env ND_SCANSCHEDULE=1h. 4) Open http://<nas-ip>:4533, create the admin, then a normal user for TwinSpin and (if offered) an API key. 5) Control Panel > External Access > DDNS > Add > provider Synology > <name>.synology.me, tick 'Get a certificate from Let's Encrypt and set it as default'. 6) Control Panel > Login Portal > Advanced > Reverse Proxy > Create: Source HTTPS music.<name>.synology.me port 443 → Destination HTTP localhost 4533. In Control Panel > Security > Certificate > Settings, make sure that hostname uses the Let's Encrypt certificate. 7) Router: forward TCP 443 (and 80 for certificate issue/renewal) to the NAS. On the LAN you need NAT loopback, or a local DNS override (router or Synology DNS Server) pointing the name at the LAN IP. No-port-forward alternative: Tailscale on the NAS and phone, then 'tailscale serve --bg --https=443 http://127.0.0.1:4533' gives https://<nas>.<tailnet>.ts.net with a valid certificate. 8) TwinSpin: Sources > Music server > https://music.<name>.synology.me + user + password, or the API key.
- **browserConstraints**: CORS: Navidrome sends Access-Control-Allow-Origin: *. Use GET with auth in the query string, with no custom headers and no cookies, so these are CORS simple requests with no preflight. Mixed content: the server URL must be https with a publicly trusted certificate. Then it works in iPhone Safari, Android Chrome and desktop. http://<nas-ip>:4533 works only in Chrome 142+ after the user allows Local Network Access (the private IP literal is exempt from mixed content once permission is granted). It never works in iPhone Safari or Firefox. LNA: if the hostname resolves to a private IP (LAN DNS override) or to Tailscale 100.64/10, Chrome 142+ shows a one-time 'access devices on your local network' prompt for ranama.github.io. If the user blocks it, requests fail. Check navigator.permissions.query({name:'local-network'}) and explain. The service worker (sw.js) ignores other origins, so nothing changes there. index.html has no CSP, so there are no connect-src limits.
- **apiDetails**: Base https://HOST/rest/<method>.view?u=USER&t=md5(password+salt)&s=SALT&v=1.16.1&c=TwinSpin&f=json. Or OpenSubsonic apiKey=KEY, which Navidrome supports; never send it together with u/p/t/s, because Navidrome rejects that mix. Methods: ping; getMusicFolders; getArtists; getArtist?id=; getAlbum?id=; getAlbumList2?type=alphabeticalByName|newest|random&size=500&offset=N; search3?query=Q&songCount=50&albumCount=20&artistCount=20; getRandomSongs?size=; getPlaylists / getPlaylist?id=; getCoverArt?id=&size=300 (an image); download.view?id=SONG (original bytes, best for decodeAudioData); stream.view?id=&format=raw, or &format=mp3&maxBitRate=320 to transcode formats the browser can't decode or to save bandwidth away from home. JSON wrapper: {'subsonic-response':{status:'ok'|'failed', error:{code,message}}}. Codes: 40 wrong credentials, 70 not found. Client design: AbortController per download; 1 or 2 parallel downloads on phones; progress from Content-Length; store {source:'subsonic', server, id, suffix, bitRate} alongside the Blob so re-imports dedupe.
- **pros**: The only in-app NAS integration that works on every target browser with no NAS hacks. Navidrome ships CORS itself, so DSM updates can't break it. Browse by artist, album, genre and playlist plus search and cover art. Server-side transcoding for weak links and odd formats. API keys mean no password stored in the browser. The same connector works with any Subsonic/OpenSubsonic server (Navidrome, Gonic, Airsonic, Ampache, LMS) on any NAS brand or PC. No DSM account or session is exposed to TwinSpin.
- **cons**: Needs a Container Manager-capable model and about 15 to 30 minutes of NAS setup: a container, DDNS, certificate, reverse proxy and router forward. Exposes one HTTPS service to the internet (Navidrome has login rate limiting; keep it updated). LAN use of the DDNS name needs NAT loopback or split DNS. Remote speed is capped by home upload bandwidth. A second index of the library (Navidrome's), separate from Audio Station's.
- sources: https://github.com/navidrome/navidrome/blob/master/server/middlewares.go https://github.com/navidrome/navidrome/blob/master/server/subsonic/middlewares.go https://www.navidrome.org/docs/installation/docker https://mariushosting.com/how-to-install-navidrome-on-your-synology-nas/ http://www.subsonic.org/pages/api.jsp https://opensubsonic.netlify.app/ https://www.synology.com/en-uk/releaseNote/ContainerManager https://mariushosting.com/synology-how-to-enable-https-on-dsm-7/ https://tailscale.com/docs/reference/tailscale-cli/serve https://developer.chrome.com/blog/local-network-access
### C. Native DSM File Station Web API connector behind a self-installed CORS front door
- **howItWorks**: TwinSpin logs in with SYNO.API.Auth (format=sid), lists or searches the music share with SYNO.FileStation.List/Search, and downloads files with SYNO.FileStation.Download. DSM itself never sends CORS headers, so the calls must go through a small proxy on the NAS that (a) forwards only /webapi/* to 127.0.0.1:5000, (b) adds Access-Control-Allow-Origin: https://ranama.github.io (plus http://localhost:8100), (c) answers OPTIONS with 204, and (d) strips or overrides the browser's Origin/Referer request headers in case DSM 7.2.2+ CSRF hardening rejects foreign origins.
- **userSetup**: Common steps: (1) Control Panel > User > Create 'twinspin', a non-admin user. Shared folder permissions: Read-only on music, No access elsewhere. Applications: allow File Station only (plus Audio Station if approach D is used). (2) DDNS + Let's Encrypt + router 443 as in B. (3) Pick ONE front door. C1 Docker (survives updates): a Caddy container (network_mode: host) listening on 127.0.0.1:8088 with a Caddyfile that sets header Access-Control-Allow-Origin 'https://ranama.github.io', header Vary Origin, an @pre method OPTIONS matcher with respond @pre 204, and 'reverse_proxy /webapi/* 127.0.0.1:5000 { header_up -Origin  header_up -Referer }'. Then add a DSM reverse-proxy rule https://nasapi.<name>.synology.me:443 → http://localhost:8088. C2 SSH, no Docker: create /usr/local/etc/nginx/sites-enabled/twinspin-cors.conf containing 'server { listen 127.0.0.1:8089; location /webapi/ { if ($request_method = OPTIONS) { add_header Access-Control-Allow-Origin https://ranama.github.io always; add_header Access-Control-Allow-Methods "GET, POST" always; return 204; } add_header Access-Control-Allow-Origin https://ranama.github.io always; proxy_set_header Origin ""; proxy_set_header Referer ""; proxy_pass http://127.0.0.1:5000; } }'. Run 'nginx -t' then 'nginx -s reload', and add a DSM reverse-proxy rule → localhost:8089. Re-check after every DSM update. C3 Web Station + PHP 8.x, no Docker: a single bridge script under /web that lists and streams the music folder with its own token and sends ACAO. The http user needs read access to the music share, and the share path must be added to the PHP profile's open_basedir. This is a custom protocol, not the DSM API. (4) Optionally enable 2FA for the twinspin user. Keep Control Panel > Security > Account > Auto block on.
- **browserConstraints**: Without the front door: every fetch to https://<nas>:5001/webapi/... fails with an opaque CORS error, because the response has no ACAO (community reports; no DSM setting exists). With the front door: use format=sid and pass _sid as a query parameter. Never rely on the DSM 'id' cookie: cross-site cookies are blocked by Safari ITP and Chrome third-party cookie rules, and credentialed CORS would need a specific origin plus Allow-Credentials. Log in with POST and Content-Type application/x-www-form-urlencoded; that is a simple request and keeps the password out of URLs and logs. Use GET for everything else. Pass SynoToken as a query parameter, not the X-SYNO-TOKEN header, which would trigger a preflight. HTTPS and a valid certificate are required on iPhone. Self-signed https://<lan-ip>:5001 fails in fetch with no click-through, and Let's Encrypt can't issue certificates for IPs. http://<lan-ip>:5000 is blocked as mixed content, except in Chrome 142+ after LNA permission, and even then CORS is still missing. DSM sessions are IP-bound: error 150, 'Request source IP does not match the login IP', when a phone switches Wi-Fi/LTE or iCloud Private Relay changes the exit IP, so re-login transparently.
- **apiDetails**: Discovery: GET /webapi/query.cgi?api=SYNO.API.Info&version=1&method=query&query=SYNO.API.Auth,SYNO.FileStation.List,SYNO.FileStation.Search,SYNO.FileStation.Download. On DSM 7, entry.cgi also serves Info; always use the returned path and maxVersion. LOGIN (DSM 7 guide recommends v6): POST /webapi/entry.cgi with body api=SYNO.API.Auth&version=6&method=login&account=U&passwd=P&session=FileStation&format=sid&enable_syno_token=yes. With 2FA add &otp_code=123456&enable_device_token=yes&device_name=TwinSpin-<device>. Next logins skip OTP with &device_name=TwinSpin-<device>&device_id=<did>. Response data: {sid, did, synotoken, is_portal_port}. Auth errors: 400 bad account/password, 401 disabled, 402 denied permission, 403 OTP required, 404 OTP failed, 406 OTP enforced (must set up 2FA), 407 blocked IP, 408/409/410 password expired or must change. Common errors: 105 no permission, 106 timeout, 107 duplicate login, 119 invalid session, 150 IP mismatch → re-login. The sid expires after 7 days by default (File Station guide). LOGOUT: GET /webapi/entry.cgi?api=SYNO.API.Auth&version=6&method=logout&session=FileStation&_sid=SID. SHARES: GET /webapi/entry.cgi?api=SYNO.FileStation.List&version=2&method=list_share&additional=["real_path"]&_sid=SID&SynoToken=T. LIST FOLDER: api=SYNO.FileStation.List&version=2&method=list&folder_path="/music/House"&offset=0&limit=1000&sort_by=name&filetype=all&additional=["size","time","type"]. v2 takes JSON-encoded values (quoted strings, arrays), URL-encoded. Filter audio extensions client-side, because a 'pattern' glob would also hide folders. RECURSIVE: api=SYNO.FileStation.Search&version=2&method=start&folder_path=["/music"]&recursive=true&extension="mp3,m4a,aac,flac,wav,aif,aiff,ogg,opus"&filetype="file" returns {taskid}. Poll method=list&taskid=ID&offset=&limit=500&additional=["size","time"] until data.finished=true, then method=stop and method=clean&taskid=ID. DOWNLOAD: GET /webapi/entry.cgi?api=SYNO.FileStation.Download&version=2&method=download&path=["/music/House/track.mp3"]&mode=download&_sid=SID. One path returns the raw file; several are zipped. mode=open sets a MIME type from the extension and returns 404 on error. Then fetch → arrayBuffer → decodeAudioData.
- **pros**: Uses DSM's own accounts and permissions and the plain folder structure. No Navidrome and no second index. C2 and C3 work on NAS models without Container Manager. Official, documented, stable API (File Station API since DSM 6; Auth v6 documented for DSM 7).
- **cons**: Every variant needs NAS tinkering. C2 can be wiped by DSM updates (KeeWeb's WebDAV CORS edits were reset by an update), and C3 means TwinSpin maintaining server code. It exposes DSM's authentication endpoint to the internet. 2FA, the 7-day sid and IP-bound sessions add UX edge cases. DSM 7.2.2-72806 fixed a WebAPI CSRF flaw (SA-24:27, CVE-2024-45538) in an undocumented way, so cross-origin requests may be rejected unless the proxy rewrites Origin; test this. No artist/album metadata without approach D.

### D. Audio Station API (browse by artist/album, transcode) through the same CORS front door as C
- **howItWorks**: Same session as C (session=AudioStation, or reuse the sid), calling Audio Station's CGI endpoints. Audio Station must be installed and indexing the music share, and the user needs the Audio Station application privilege. Gives library-style browsing and on-the-fly transcoding. Synology publishes no docs for it; the details come from reverse engineering.
- **userSetup**: Everything from C. Also install Audio Station (its spec page lists DSM 7.2, 7.3 and 7.4), add the music share to the indexed folders (Control Panel > Indexing Service), and allow Audio Station for the twinspin user.
- **browserConstraints**: Identical to C. Without the front door, cross-origin <audio src=stream.cgi...> would play, but Web Audio gets silence from a non-CORS cross-origin media element, and decodeAudioData needs readable bytes. So a CORS proxy is mandatory for TwinSpin's DJ features.
- **apiDetails**: Resolve paths via SYNO.API.Info (typically AudioStation/<x>.cgi). SONGS: /webapi/AudioStation/song.cgi api=SYNO.AudioStation.Song&version=3&method=list&library=all|personal&offset=0&limit=500&sort_by=title|artist|random&sort_direction=ASC&additional=song_tag,song_audio,song_rating, with filters artist=, album=, album_artist=, genre=. ALBUMS: AudioStation/album.cgi api=SYNO.AudioStation.Album&version=3&method=list&library=all&sort_by=name|year|time&artist=&genre=. ARTISTS: AudioStation/artist.cgi version=3 method=list (album artists). FOLDERS: AudioStation/folder.cgi api=SYNO.AudioStation.Folder&version=2&method=list&library=all&id=dir_1609 (omit id for root). SEARCH: AudioStation/search.cgi api=SYNO.AudioStation.Search&version=1&method=list&keyword=Q returns albums, artists and songs. COVER: AudioStation/cover.cgi api=SYNO.AudioStation.Cover&version=1&method=getsongcover&id=music_123&library=all. STREAM original: AudioStation/stream.cgi?api=SYNO.AudioStation.Stream&version=2&method=stream&id=music_123&_sid=SID. TRANSCODE: /webapi/AudioStation/stream.cgi/0.mp3?api=SYNO.AudioStation.Stream&version=2&method=transcode&id=music_123&format=mp3&_sid=SID. Song ids containing _v_ are cue-split virtual tracks and need transcode. Audio Station transcodes to 16-bit only.
- **pros**: Library browsing and transcoding without Docker. Reuses Audio Station's existing index, plus covers and lyrics.
- **cons**: Undocumented and could change without notice (the parameters come from packet captures). Has every cost of C. More API surface to maintain than Subsonic. Navidrome (B) gives the same features through a documented, CORS-enabled API.

### E. Direct DSM API from GitHub Pages with no NAS changes (LAN IP, self-signed :5001, DDNS, QuickConnect) — NOT VIABLE
- **howItWorks**: TwinSpin fetches https://<host>:5001/webapi/... directly. Every variant fails on CORS even when connectivity works. Connectivity notes: (1) http://<lan-ip>:5000 from an https page is mixed content: blocked in Safari and Firefox, and allowed in Chrome 142+ only for private-IP literals or .local hosts after LNA permission. (2) https://<lan-ip>:5001 uses a self-signed or mismatched certificate, which fetch rejects without a prompt; phones need a CA profile installed and fully trusted. (3) https://<name>.synology.me:5001 with Let's Encrypt plus port forwarding works at the TLS level. (4) QuickConnect: the browser can't resolve the ID. I tested global.quickconnect.to/Serv.php on 2026-10-16: POST returns JSON with no Access-Control-Allow-Origin, and OPTIONS returns 404. The relay is bandwidth-limited and only exposes Synology services.
- **userSetup**: Not applicable. Don't build this. DDNS + Let's Encrypt is still the connectivity layer that B and C build on: Control Panel > External Access > DDNS > Synology provider > tick 'Get a certificate from Let's Encrypt and set it as default'. Ports 80/443 must reach the NAS for issue and renewal.
- **browserConstraints**: CORS: no Access-Control-Allow-Origin on /webapi, so response bodies are unreadable. mode:'no-cors' gives opaque responses that can't be parsed or decoded. LNA (Chrome 142, Oct 28 2025): public site → RFC1918, 100.64/10 (CGNAT/Tailscale), link-local or .local addresses triggers a permission prompt in a secure context. Granting it never replaces CORS. iPhone Safari has no LNA exemption and blocks mixed content outright.
- **apiDetails**: See C for endpoints. Tested on 2026-10-16: curl -X OPTIONS https://global.quickconnect.to/Serv.php → 404, no CORS headers. POST {command:'get_server_info',...} → 200 text/plain with no Access-Control-Allow-Origin.
- **pros**: None for TwinSpin.
- **cons**: Fails on every browser because of CORS; also mixed-content and certificate failures on phones; QuickConnect can't be used from a web page.

### F. WebDAV Server package — NOT VIABLE without an extra proxy
- **howItWorks**: WebDAV on 5005 (HTTP) or 5006 (HTTPS). TwinSpin would PROPFIND folders and GET files.
- **userSetup**: Package Center > WebDAV Server > enable HTTPS 5006. CORS would also need SSH edits to the package's httpd config (alexanderharm/syno-webdav-keeweb reapplies them hourly via Task Scheduler) or a HAProxy container that answers OPTIONS.
- **browserConstraints**: No CORS by default. Basic auth needs an Authorization header, and PROPFIND is a non-simple method, so the browser always sends a preflight. Synology's WebDAV backend doesn't handle OPTIONS preflight: it hangs and the reverse proxy returns 504. fetch() also forbids credentials embedded in the URL.
- **apiDetails**: PROPFIND /music/ with Depth: 1 and Authorization: Basic ... → XML multistatus. GET /music/file.mp3. All of these need CORS on both the preflight and the actual response.
- **pros**: A standard protocol and a generic client.
- **cons**: Preflight breaks it, and the CORS fixes are hacks that DSM or package updates reset. It needs the same amount of NAS work as B or C, with more fragility.
- sources: https://tevinzhang.com/en/fix-cors-for-synology-webdav-no-nginx-hacks/ https://github.com/keeweb/keeweb/issues/703 https://github.com/alexanderharm/syno-webdav-keeweb
### G. File Station / Audio Station public share links (gofile.me, /sharing/, /fbsharing/) — NOT VIABLE for TwinSpin
- **howItWorks**: The user shares files or a folder. gofile.me is Synology's own short-link domain; it redirects to the NAS sharing page through QuickConnect or DDNS. SYNO.FileStation.Sharing returns URLs like http://myds.com:5000/fbsharing/<id>.
- **userSetup**: File Station > right-click > Share > copy the link (optional password and expiry).
- **browserConstraints**: Share pages and downloads send no CORS headers. An <audio> element can play a direct file URL cross-origin, but Web Audio gets silence from non-CORS media, and decodeAudioData can't read the bytes. Single-file links open an HTML download page, not raw bytes. The direct-file URL format is undocumented and unverified.
- **apiDetails**: SYNO.FileStation.Sharing (version 3) method=create&path=... returns {links:[{id,url,qrcode,...}]}.
- **pros**: No login needed in TwinSpin.
- **cons**: No library browsing, no CORS, breaks Web Audio and decoding, and links are public by design.
- sources: https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf https://mariushosting.com/synology-how-to-create-a-shared-link-on-dsm-7/ https://webaudio.github.io/web-audio-api/#MediaElementAudioSourceNode
### H. Host TwinSpin on the NAS so it is same-origin with DSM (no CORS needed)
- **howItWorks**: Same origin means same scheme, host and port. Web Station serves its own site on 80/443 or on portal hosts and ports, while DSM is on 5000/5001 or a Login Portal hostname, so Web Station is still a different origin. Three real same-origin variants: (1) a custom DSM package (.spk) whose UI is served by DSM itself under https://<nas>:5001/webman/3rdparty/TwinSpin/. That is same-origin with /webapi and can reuse the logged-in DSM session (SYNO.API.Auth method=token returns SynoToken). (2) A custom nginx server block (as in C2) that serves the TwinSpin files at / and proxies /webapi/ to 127.0.0.1:5000. (3) Tailscale: 'tailscale serve' with --set-path / pointing at the TwinSpin folder and --set-path /webapi pointing at http://127.0.0.1:5000/webapi, which gives https://<nas>.<tailnet>.ts.net. Serving files from /volume1 may hit permission issues under DSM's sandboxed Tailscale user; unverified.
- **userSetup**: (1) Install an unsigned community .spk manually. DSM 7 shows a 'third-party, not verified by Synology' warning. TwinSpin would need to publish the package. (2) The SSH steps from C2 plus copying the TwinSpin build to the NAS. (3) The Tailscale package plus HTTPS enabled in the tailnet admin; every phone runs the Tailscale app.
- **browserConstraints**: No CORS within the same origin. The IndexedDB library, settings and service worker are per-origin, so the NAS-hosted copy has a different library from ranama.github.io. Needs a valid certificate on phones (DDNS + Let's Encrypt, or ts.net). The Tailscale variant triggers the Chrome LNA prompt because 100.64/10 counts as 'local'.
- **apiDetails**: Same as C, but with no proxy headers needed. In the .spk variant, use session cookies and SynoToken from GET /webapi/entry.cgi?api=SYNO.API.Auth&version=6&method=token.
- **pros**: No CORS at all; the .spk variant uses DSM's own login (no password in TwinSpin). Works fully on LAN.
- **cons**: Splits the user's library across two origins. A package or deploy pipeline to maintain. Variant (2) is fragile across DSM updates, and the .spk paths are not verified for DSM 7.3/7.4. A heavy fix for one user's NAS.
- sources: https://docs.synocommunity.com/user-guide/installation/ https://www.synology.com/en-us/dsm/7.4/software_spec/web_station https://tailscale.com/docs/reference/tailscale-cli/serve https://tailscale.com/kb/1153/tailscale-cert https://wicg.github.io/local-network-access/
## Findings
- [high,critical] DSM's web server sends no Access-Control-Allow-Origin on /webapi, and DSM 7.2/7.3/7.4 has no setting to enable CORS. So https://ranama.github.io cannot read any DSM API response (login, list, download) directly. Community answer: the response from the Synology API itself must carry the CORS header. Dashboards like Homepage call DSM server-side for this reason.
- [medium,critical] Control Panel > Login Portal > Advanced > Reverse Proxy > Custom Header entries are request headers sent to the backend (rendered as proxy_set_header; the WebSocket preset adds Upgrade $http_upgrade and Connection $connection_upgrade). They cannot add a CORS response header, and the reverse proxy can't short-circuit OPTIONS preflight. One blog claims they are response headers; Synology's KB doesn't say either way.
- [high,critical] Navidrome (a Subsonic/OpenSubsonic server that runs in Synology Container Manager) sets CORS AllowedOrigins ['*'], AllowedHeaders ['*'] and AllowCredentials false on all routes, and supports OpenSubsonic apiKey auth. A static GitHub Pages app can therefore browse and download from it with no NAS hacks once it has HTTPS. Checked in the master source on 2026-10-16.
- [medium,critical] Zero-code path: the iPhone Files app connects to NAS SMB shares natively (iOS 13+, needs SMB2+; set the NAS max protocol to SMB3 if it errors). The Synology Drive iOS app exposes Drive folders, including Team Folders, in the Files app (release notes 3.5.0, 3.7.2, 3.8.0). Safari's <input type=file> uses the same system document picker, so TwinSpin's existing Add music button should be able to pick NAS files. This still needs a test on a device.
- [medium] Android has no built-in SMB location in the system picker. CIFS Documents Provider (open source, v2.4.0, Oct 2025, Android 8+) exposes SMB/FTP/SFTP shares through the Storage Access Framework, so Chrome's file chooser can pick NAS files. Whether the Synology Drive Android app registers as a documents provider is unconfirmed.
- [high] DSM 7 login API: POST or GET /webapi/entry.cgi api=SYNO.API.Auth version=6 (supports 3 to 7) method=login with account, passwd, session, format=sid|cookie, otp_code, enable_syno_token=yes, enable_device_token=yes, device_name, device_id. Response {sid, did, synotoken, is_portal_port}. Pass _sid and SynoToken on later calls. Errors: 400 bad credentials, 401 disabled, 402 denied, 403 OTP required, 404 OTP wrong, 406 OTP enforced, 407 IP blocked, 408 to 410 password expired. Common errors: 105 no permission, 106 timeout, 107 duplicate login, 119 invalid session, 150 source IP differs from login IP.
- [high] File Station API (official, since DSM 6, entry.cgi, version 2). List method=list_share and method=list (folder_path, offset, limit, sort_by, filetype=file|dir|all, pattern glob, additional=[real_path,size,owner,time,perm,type,mount_point_type] as a JSON array). Search is non-blocking: start(folder_path[], recursive, pattern, extension, filetype) returns taskid; list(taskid) until finished; then stop and clean. Download method=download with path (JSON array) and mode=open|download; one file is returned raw, several are zipped. The sid expires after 7 days by default.
- [high] CORS mechanics for a DSM connector: a GET with _sid and SynoToken in the query, and a POST login with application/x-www-form-urlencoded, are CORS simple requests (no preflight), but the response still needs ACAO. Cookie auth would need credentials:'include', a specific origin and Allow-Credentials, and fails under Safari ITP and third-party cookie blocking, so use format=sid. The X-SYNO-TOKEN header would force a preflight.
- [high,critical] Mixed content and Local Network Access: an https page cannot fetch http://<nas>:5000 in Safari or Firefox. Chrome 142+ (Oct 28 2025) gates public→local requests behind a permission prompt; local means RFC1918, 100.64.0.0/10 including Tailscale, link-local and .local. Once granted, it exempts only private-IP-literal or .local http URLs, or fetches with targetAddressSpace:'local', from mixed-content blocking. CORS is still enforced. The only route that works on iPhone is a hostname with a publicly trusted certificate, such as *.synology.me + Let's Encrypt or *.ts.net.
- [high] QuickConnect can't be used by a web page. I tested on 2026-10-16: global.quickconnect.to/Serv.php (the ID resolver) returns no Access-Control-Allow-Origin, and OPTIONS returns 404. The relay is bandwidth-limited and undocumented for third parties. It works only for Synology's native apps, for example the Synology Drive app in the zero-code route.
- [high] Web Audio needs CORS. A cross-origin <audio> without CORS plays, but MediaElementAudioSourceNode outputs silence, and decodeAudioData needs readable bytes. A 'no-CORS' NAS link therefore can't feed TwinSpin's decks.
- [medium] The WebDAV Server package has no CORS option. Browser preflight (OPTIONS) to it hangs until the proxy returns 504. Manual CORS edits to its httpd config were reset by DSM or package updates. Basic auth always triggers a preflight.
- [medium] Custom nginx configs placed in /usr/local/etc/nginx/sites-enabled/* or conf.d/http.*.conf (server blocks) are not overwritten by the Login Portal UI. The UI-generated server.ReverseProxy.conf is regenerated, so manual edits there are lost. Whether custom files survive major DSM updates is not guaranteed.
- [low] DSM 7.2.2-72806 and 7.2.1-69057-2 fixed a WebAPI CSRF flaw where the request origin was not checked (SA-24:27, CVE-2024-45538, CVSS 9.6). The fix isn't documented, so a CORS front door should strip or override the browser's Origin/Referer, and the client should send SynoToken. Separately, DSM's 'Improve protection against cross-site request forgery attacks' option makes SynoToken required.
- [medium] DSM WebAPI sessions are bound to the login IP (error 150). Phones moving between Wi-Fi and cellular, or Safari's iCloud Private Relay changing the exit IP, can invalidate the sid, so a DSM connector must re-login silently. Not an issue for Subsonic, where every request carries its own auth.
- [medium] The Audio Station API (SYNO.AudioStation.Song/Album/Artist/Folder/Search/Cover/Stream under AudioStation/*.cgi; stream version 2 with method=stream|transcode&format=mp3) is undocumented and reverse-engineered. Audio Station is still supported on DSM 7.2, 7.3 and 7.4. DSM 7.4 was released on June 16, 2026.
- [medium] Container Manager (needed for Navidrome or a Caddy CORS proxy) requires DSM 7.2+. It runs on x86 Plus models and, per Synology's release notes, on some ARMv8 models (DS223, DS420j, DS220j, DS120j). Check the user's model before recommending B or C1.
- [medium] Tailscale has an official Synology package (Package Center). It gives remote access without port forwarding, using 100.64.0.0/10 addresses and *.ts.net names. 'tailscale serve --https=443 http://127.0.0.1:<port>' provides a valid TLS certificate (proxies only to 127.0.0.1). Every client device needs the Tailscale app, and Chrome shows the LNA prompt because 100.64/10 counts as local.
