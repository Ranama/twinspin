# verify-synology
- **partly-true**: 1. DSM /webapi sends no Access-Control-Allow-Origin, and DSM 7.2/7.3/7.4 has no CORS setting, so ranama.github.io cannot read DSM API responses directly. Homepage calls DSM server-side for this reason.
  - CORRECTION: The main point holds. I found no CORS setting anywhere. The DSM 7.3 and 7.4 release notes never mention CORS, cross-origin or reverse-proxy headers (checked up to 7.4.1-90080 Update 1, 2026-10-12, and 7.3.2-86009 Update 5). The official Login and File Station guides say nothing about CORS. The community 'syno' JS wrapper tells browser users to disable the same-origin policy. I had no NAS to test, so 'sends no ACAO' rests on indirect evidence. Homepage does proxy every widget call server-side, including its synologyProxyHandler, but by design to keep credentials out of the browser. Avoiding CORS is a side effect, so 'for this reason' overstates it.
- **confirmed**: 2. Login Portal reverse-proxy Custom Header entries are request headers (proxy_set_header), and the WebSocket preset adds Upgrade/Connection. They cannot add a CORS response header or short-circuit OPTIONS.
  - CORRECTION: Community sources (not a Synology KB) show the UI rendering 'proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection $connection_upgrade;' into the location block. Every vendor guide uses the tab for request headers such as X-Forwarded-Proto and X-Forwarded-Host. A synoforum user who hand-added 'add_header Access-Control-Allow-Origin' to the generated file got no working result. I found no Synology KB wording either way. The 'one blog says response headers' detail is unverified.
- **partly-true**: 3. Navidrome sets CORS AllowedOrigins ['*'], AllowedHeaders ['*'] and AllowCredentials false on all routes, and supports OpenSubsonic apiKey auth, so a GitHub Pages app can browse and download from it.
  - CORRECTION: The CORS part is confirmed in both master and the latest release v0.64.2 (2026-09-24). corsHandler() is in defaultMiddlewares on s.router, and MountRouter mounts every sub-router (including /rest) on it. It allows HEAD, GET, POST, PUT, PATCH and DELETE, and exposes x-content-duration, x-total-count and x-nd-authorization. The API key part is wrong for released builds. OpenSubsonic API key auth (PR #6219) was merged to master on 2026-09-28, after v0.64.2, and master is 37 commits ahead. No stable release or :latest Docker image has apiKey yet. TwinSpin must support classic Subsonic token auth (u + t=md5(password+salt) + s) as the default and treat apiKey as optional. In master, keys are per-player, prefixed 'nds_', and managed under Settings > 'Players & API keys'. Sending apiKey together with u/p/t/s returns error 43.
- **partly-true**: 4. The iPhone Files app connects to SMB natively (iOS 13+, SMB2+). The Synology Drive iOS app exposes Drive folders and Team Folders in Files (3.5.0, 3.7.2, 3.8.0). Safari's file input uses the same picker, so 'Add music' can pick NAS files.
  - CORRECTION: Confirmed: SMB 'Connect to Server' arrived in iOS 13 and needs SMB 2.0 or later. The 'set max SMB3' fix is a single user anecdote. Synology Drive 3.5.0 notes do refer to 'Synology Drive folders in the iOS Files app': a passcode lock and a fix for offline opening. I could not verify the 3.7.2 or 3.8.0 Team Folder claims. Synology's iOS release-note feed returns empty, and the App Store and blog notes for 3.8.x/3.9.0 don't mention Files or Team Folders. Note that Synology Drive iOS 3.9.0 (App Store, 2026-08-11) now requires iOS 18 or later. A device test is still needed.
- **partly-true**: 5. Android has no built-in SMB picker location. CIFS Documents Provider (open source, v2.4.0, Oct 2025, Android 8+) exposes SMB/FTP/SFTP through SAF. Whether Synology Drive Android is a documents provider is unconfirmed.
  - CORRECTION: The date is wrong. v2.4.0 was published 2025-05-12, not October 2025. It is still the latest version on GitHub and F-Droid (versionCode 31), and the repo has had no commits since 2025-05-11. minSdk is 26 (Android 8.0), as claimed. SMB encryption via SMBJ was added in 2.4.0, SFTP in 2.2.0, FTP/FTPS in 2.1.0. Whether the Synology Drive app is a documents provider is still unconfirmed. A fallback that does work: Synology Drive Android 'sync tasks' can sync a NAS folder to phone storage, and Chrome's file picker can then pick from there.
- **confirmed**: 6. DSM 7 login API: entry.cgi SYNO.API.Auth version 6 (3-7) with account, passwd, session, format, otp_code, enable_syno_token, enable_device_token, device_name, device_id; response sid, did, synotoken, is_portal_port; auth errors 400-410; common errors 105/106/107/119/150.
  - CORRECTION: Everything matches the official DSM Login Web API Guide (dated Apr 19, 2023): 'Version: 3 - 7; 6 (Recommended)', 'Since DSM 6.0', and the full 400-410 and 100-150 tables, including 150 'Request source IP does not match the login IP'. One detail matters: the default format is cookie, so the client must pass format=sid explicitly. The guide's examples use GET. POST is only implied by 'GET/POST method with _sid argument'.
- **confirmed**: 7. File Station API (DSM 6+, entry.cgi, v2): list_share/list params; non-blocking Search start/list/stop/clean; Download with path array and mode open|download, one file raw and several zipped; sid expires after 7 days by default.
  - CORRECTION: All confirmed by the official File Station guide. Notes: the default download mode is 'open', which sets Content-Type to the file's MIME type. The example sends mode JSON-quoted (mode=%22open%22). With mode=open, errors come back as HTTP 404 rather than JSON. The 7-day sid expiry appears in the guide's older SYNO.API.Auth section ('The applied sid will expire after 7 days by default').
- **partly-true**: 8. GET with _sid/SynoToken in the query and a form-urlencoded POST login are CORS simple requests, but still need ACAO. Cookie auth needs credentials:'include' plus a specific origin and Allow-Credentials, and fails under Safari ITP and third-party cookie blocking, so use format=sid. An X-SYNO-TOKEN header would force a preflight.
  - CORRECTION: The CORS mechanics are correct, and the official guide allows SynoToken as a query parameter, so no custom header is needed. One correction: Chrome does not block third-party cookies by default. In April 2025 Google announced it would keep them and drop the standalone prompt. Cookie auth in Chrome would instead depend on DSM's 'id' cookie having SameSite=None; Secure, which I did not verify. Safari and Firefox block it. The conclusion (use format=sid) is unchanged.
- **confirmed**: 9. Mixed content and Local Network Access: https cannot fetch http://nas:5000 in Safari or Firefox. Chrome 142+ (Oct 28 2025) gates public→local behind a permission. 'Local' covers RFC1918, 100.64/10, link-local and .local. Once granted, only private-IP literals, .local or targetAddressSpace fetches are exempt from mixed content. CORS still applies. On iPhone only a publicly trusted HTTPS hostname works.
  - CORRECTION: The WICG LNA spec lists 100.64.0.0/10, 169.254/16, fc00::/7 and fe80::/10 as 'local'. MDN and the Chrome blog confirm the three mixed-content exemptions and that 'if local network access permissions are not granted, mixed content checks still apply'. Missing nuance: a public HTTPS hostname that resolves to a local address also triggers Chrome's LNA prompt on desktop and Android. That covers *.synology.me via NAT hairpin or split DNS at home, and *.ts.net or any Tailscale 100.x address. TwinSpin must handle a denied prompt even on the HTTPS route. Chrome 145 split the setting into 'Apps on device' (loopback) and 'Local network'. On iPhone, a private CA installed as a trusted profile would also work, but it is impractical.
- **partly-true**: 10. QuickConnect can't be used by a web page: global.quickconnect.to/Serv.php returns no ACAO, OPTIONS returns 404, the relay is bandwidth-limited and undocumented, and it works only for Synology's native apps.
  - CORRECTION: I re-ran the live test on 2026-10-16. A POST to https://global.quickconnect.to/Serv.php with Origin: https://ranama.github.io returned 200 text/plain and no Access-Control-* headers. OPTIONS returned '404 page not found'. Synology describes the relay only as 'may be slower ... because of increased network latency', with no published bandwidth cap. 'Works only for native apps' is wrong: QuickConnect also serves DSM's own web UI in any browser (quickconnect.to/<ID>). It just can't be used cross-origin by a third-party page.
- **confirmed**: 11. Web Audio needs CORS: a cross-origin <audio> without CORS plays, but MediaElementAudioSourceNode outputs silence, and decodeAudioData needs readable bytes.
  - CORRECTION: The Web Audio spec §1.22.4 says a MediaElementAudioSourceNode 'MUST output silence' when the media element's resource was fetched CORS-cross-origin. decodeAudioData needs an ArrayBuffer, which an opaque no-cors fetch cannot provide.
- **partly-true**: 12. The WebDAV Server package has no CORS option; preflight hangs until a 504; manual httpd CORS edits get reset by DSM or package updates; Basic auth always triggers a preflight.
  - CORRECTION: No CORS option: supported indirectly by a community script (alexanderharm/syno-webdav-keeweb). It patches /var/packages/WebDAVServer/target/etc/httpd/conf/extra/httpd-ssl.conf-webdav and httpd.conf-webdav to add ACAO * and answer OPTIONS with 200. It runs hourly as root and re-applies any missing lines, which suggests edits get reverted. So CORS on WebDAV is achievable, just fragile. The 'preflight hangs until 504' detail is unverified. Basic auth forcing a preflight is correct, because Authorization is not a CORS-safelisted header.
- **partly-true**: 13. Custom nginx files in sites-enabled/* or conf.d/http.*.conf are not overwritten by the Login Portal UI; server.ReverseProxy.conf is regenerated; survival across major DSM updates is not guaranteed.
  - CORRECTION: Community-sourced only. The synoforum 'under the hood' tutorial shows nginx.conf including conf.d/http.*.conf, app.d/server.*.conf and sites-enabled/*. It says server.ReverseProxy.conf is re-rendered on every UI change, so manual edits are lost, and it recommends conf.d over app.d. No Synology source covers whether custom files survive DSM updates, so that remains unverified.
- **partly-true**: 14. DSM 7.2.2-72806 and 7.2.1-69057-2 fixed a WebAPI CSRF flaw where request origin was not checked (SA-24:27, CVE-2024-45538, CVSS 9.6). A proxy should strip Origin/Referer. The 'Improve protection against CSRF' option makes SynoToken required.
  - CORRECTION: Confirmed: SA-24:27 (published 2024-11-27, details disclosed 2025-12-04/05) lists CVE-2024-45538, CWE-352, CVSS 9.6, fixed in 7.2.2-72806, 7.2.1-69057-2 and DSMUC 3.1.4-23079. Unverified: 'origin was not checked'. Synology and NVD say only 'via unspecified vectors', so the advice to strip Origin/Referer is speculation and needs testing against a real NAS. Confirmed: the login guide says to pass SynoToken when 'Improve protection against cross-site request forgery attacks' is on.
## Extra findings
- High impact for the recommendation: Navidrome API keys exist only in master (PR #6219, merged 2026-09-28). The latest release, v0.64.2 (2026-09-24), and the :latest Docker image do not have them. The 'Navidrome user plus an API key' setup step and an apiKey-first connect sheet will fail on stable installs. Build u + t/s token auth (t = md5(password + salt)) as the default and detect apiKeyAuthentication via getOpenSubsonicExtensions.
- CORS on Navidrome is confirmed in the released v0.64.2 source, not only in master: middlewares.go lines 90-104, plus server.go defaultMiddlewares and MountRouter.
- Current DSM versions as of 2026-10-16: 7.4.1-90080 Update 1 (2026-10-12), 7.4-90075 (2026-06-16), 7.3.2-86009 Update 5 (2026-10-12), 7.2.2-72806 Update 10 (2026-10-12). Release notes source: synology.com/api/releaseNote/findChangeLog?identify=DSM.
- Chrome LNA also applies to HTTPS routes. If music.<name>.synology.me resolves to a LAN IP at home (NAT hairpin or split DNS), or if Tailscale/*.ts.net (100.64.0.0/10) is used, Chrome desktop and Android show the local-network permission prompt and block fetches if it is denied. iOS Safari has no such prompt.
- Let's Encrypt for synology.me: DSM can issue a wildcard *.name.synology.me certificate via DNS-01 (since DSM 6.2.3), so opening port 80 for renewal is unnecessary with the wildcard option. Only 443, or Tailscale, is needed.
- Container Manager is not available on every Synology model. Older ARMv7 and some value or 'j' models lack it. ARMv8 support for DS223 and DS420j was added in Container Manager 20.10.23 (DSM 7.2+). The Navidrome route needs a model check: https://www.synology.com/releaseNote/ContainerManager
- Synology Drive iOS 3.9.0 requires iOS 18+ and Synology Drive Android 3.9.0 requires Android 10+ (released 2026-08 and 2026-10-13). The zero-code help card should state these minimums.
- Android zero-code alternative not in the research: Synology Drive Android sync tasks can sync a NAS music folder to local phone storage, and Chrome's file chooser can then pick from it. This works even if Drive is not a SAF documents provider.
- DSM login defaults to format=cookie. The connector must send format=sid explicitly, or the sid is only set in the 'id' cookie.
- File Station Download defaults to mode=open, which returns the file's MIME type and an HTTP 404 on error instead of JSON. TwinSpin's fetch error handling should expect this.
- CIFS Documents Provider has had no commits since May 2025, about 17 months before 2026-10-16. Treat it as maintained-but-dormant when recommending it.
- I could not test whether DSM's /webapi sends CORS headers, because no NAS was reachable. The absence of a setting is backed by documentation and release notes, not by a live header test.
