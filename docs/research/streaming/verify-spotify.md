# verify-spotify
- **confirmed**: 1. Spotify audio cannot be routed into TwinSpin's Web Audio DJ engine (Widevine/EME, no audio-data method; beatmatch/scratch/EQ/FX impossible).
  - CORRECTION: The conclusion holds, and there is a more direct reason than EME. spotify-player.js (fetched live 2026-10-13) builds a hidden iframe from https://sdk.scdn.co/embedded/index.html with allow="encrypted-media; autoplay". The media element sits in that cross-origin frame, so TwinSpin's page cannot reach it at all. EME is a second layer on top of that. The player bundle (sdk.scdn.co/embedded/index.js) supports com.widevine.alpha, PlayReady and com.apple.fps.1 (FairPlay), so the stream is not Widevine-only: Safari/iOS uses FairPlay and Edge can use PlayReady. No SDK method or event returns PCM or a MediaStream. The SDK's initialization_error is documented as most likely a browser without EME support. 'Technically impossible' slightly overstates it. A tab-audio capture hack (getDisplayMedia/tabCapture) is uncertain technically (one report says protected audio comes out muted). It would also be 'stream ripping', which Terms IV.2 forbids, so it is not a legitimate route.
- **confirmed**: 2. Policy III.7 (eff. 2025-05-15) bans segue/mix/re-mix/overlap; Terms v10 IV.2 bans modifying/derivative works and stream ripping; IV.3 limits caching; so crossfades/transitions/overlap are not allowed.
  - CORRECTION: Accurate. III.7 goes on to cover mixing with any other audio, including other Spotify content. The caching rule is IV.3.2 'Local caching': only temporary caching where strictly necessary. Spotify-to-Spotify crossfades are covered too. Not mentioned in the claim: III.13 forbids analysing Spotify Content for any purpose, so BPM, beat-map or waveform analysis is barred even if it were technically possible.
- **confirmed**: 3. Basic playback allowed: SDK creates 'a local Spotify Connect device in your browser'; Web API covers transfer/play/pause/skip/seek/volume/shuffle/repeat/add-to-queue (POST /me/player/queue, Premium, user-modify-playback-state); SDK needs 'streaming' scope + Premium; mobile-only Premium excluded.
  - CORRECTION: Accurate. The docs say the SDK is 'designed to create a local Spotify Connect device in your browser' and requires Premium, with 'mobile only types of premium subscriptions are excluded'. On the scopes page, the streaming scope is required only for the Web Playback SDK. Add-to-queue is POST /v1/me/player/queue, needs scope user-modify-playback-state and is Premium-only. Two additions. Since the February 2026 changes the user object no longer returns 'product' or 'email', so TwinSpin cannot check for Premium up front through /me. It has to rely on the SDK's account_error event. Community threads also report Lite/Premium Mini accounts failing with account_error.
- **partly-true**: 4. Dev Mode changed 2026-02-11 (new) / 2026-03-09 (existing): owner Premium, 5 users (from 25), search limit 10 (default 5), batch GETs/browse/top-tracks/other users' playlists & profiles removed, playlist items only for owned/collaborative; player endpoints unchanged.
  - CORRECTION: The dates, the owner-Premium rule, the 5-user cap, search max 10 (default 5), the removed endpoints and the unchanged player endpoints are all correct. Correction: the blog update says the endpoint-access changes were POSTPONED for existing integrations. Only Premium, the user cap and the one-Client-ID limit took effect on 2026-03-09. That does not matter for TwinSpin, because a new app gets the reduced endpoint set immediately. Feb 2026 also limited each developer to 1 Client ID (raised to 25 in July 2026). It removed per-type library save/check endpoints in favour of /me/library, renamed playlist /tracks to /items, and removed the user fields product and email. Those removals affect the Premium pre-check. external_ids (ISRC) was removed and then restored in March 2026. The '25 previously' figure comes from TechCrunch, not Spotify. The blog frames Development Mode as for 'personal projects for non-commercial use by individual developers'.
- **confirmed**: 5. Since 2025-05-15 extended quota only for organisations with launched service and >=250k MAU; review up to 6 weeks; TwinSpin stays in Dev Mode <=5 users.
  - CORRECTION: Accurate. The quota-modes page also lists other requirements: a legally registered business, availability in key Spotify markets, commercial viability, and an application sent from a company email. The criteria were announced 2025-04-15. Users who are not on the allowlist get 403 errors on API requests. Because the GitHub Pages site is public, the UI has to handle the 403 gracefully for everyone else.
- **confirmed**: 6. Static site can use Auth Code + PKCE with no secret and a browser fetch token exchange; implicit grant, HTTP and 'localhost' redirects dropped for new apps 2025-04-09 and all apps 2025-11-27; register https://ranama.github.io/twinspin/ and http://127.0.0.1:PORT (port optional for loopback).
  - CORRECTION: Accurate. A live header check on 2026-10-13 confirmed CORS works. OPTIONS and POST to https://accounts.spotify.com/api/token with Origin https://ranama.github.io returned access-control-allow-origin: https://ranama.github.io and allowed POST and Content-Type. A preflight to api.spotify.com/v1/me/player also reflected the origin and allowed PUT and Authorization. The PKCE token body is client_id, grant_type, code, redirect_uri and code_verifier, with no secret. One nuance: HTTP is still allowed for loopback IP literals (127.0.0.1 and [::1]). The 2025-11-27 cutover blog says only that new apps were 'already subject' to the rules. The 2025-04-09 date comes from the Feb 2025 blog and the redirect-URI docs. The redirect URI must match exactly, including the trailing slash.
- **confirmed**: 7. Refresh tokens expire 6 months after first authorisation; refreshing doesn't reset; new apps since 2026-06-18, existing since 2026-07-20; on invalid_grant re-run PKCE login.
  - CORRECTION: Accurate. Additional details: the token endpoint returns 400 invalid_grant and Spotify says 'do not retry the refresh'. Refresh tokens carry no issuance timestamp, so Spotify advises recording the authorization time yourself (localStorage works for TwinSpin). A refresh response may not include a new refresh_token, in which case keep using the existing one. The community thread says the rule applies to Authorization Code and PKCE flows, not Client Credentials.
- **confirmed**: 8. July 2026: client IDs per developer 1 -> 25, dev-mode quota per developer account, 429 with reason QUOTA_EXCEEDED.
  - CORRECTION: Accurate. The blog post is dated 2026-07-23. Quota is separate from the rolling 30-second rate limit, whose 429s carry Retry-After. The migration guide says existing apps are grandfathered.
- **confirmed**: 9. 2024-11-27: audio-features, audio-analysis, recommendations, related-artists, featured & category playlists, preview URLs in multi-get, algorithmic/editorial playlists closed to new apps; TwinSpin can't get BPM/beat data or un-encrypted preview MP3.
  - CORRECTION: The list is accurate. It also applies to existing dev-mode apps without a pending extension request. The blog names preview URLs only 'in multi-get responses'. However, the Get Track reference now marks preview_url as Deprecated and nullable. Community moderators say new apps get no preview URLs from any endpoint. Even with a preview, Policy III.7 (no mixing) and III.13 (no analysis) would still block DJ use.
- **confirmed**: 10. Mobile: SDK supported on Chrome/Firefox/Safari/Edge Android+iOS (since 2021-09-13); autoplay blocked until activateElement (autoplay_failed); background play limited; iOS ignores setVolume; some Android devices fail Widevine provisioning.
  - CORRECTION: Mostly accurate. Sources: the docs list of supported browsers, the 2021-09-13 'out of beta' blog (mobile support with 'limitations around autoplay and background play'), and the reference note that on iOS volume is 'always under the user's physical control' and getVolume returns 1. The docs also say playback does not start automatically after a transfer on iOS. Widevine failures ('No supported keysystem', 'Device not provisioned', 'Unable to set L1 security level') come only from community reports. They are Android-specific: iOS Safari uses FairPlay (com.apple.fps.1 in the SDK bundle), not Widevine. Brave on Android reportedly has no Widevine. Android WebViews often fail.
- **partly-true**: 11. Policy III.11 bans products that 'mimic, or replicate or attempt to replace a core user experience of Spotify'; a full replacement player is a grey area; keep minimal, credit, show art/metadata (II.5), link back (II.4).
  - CORRECTION: The quotes and section numbers are correct. Calling it a 'grey area' understates the risk. The user's stated goal, listening on TwinSpin 'instead of their app', is almost word for word the 'attempt to replace a core user experience' that III.11 bans without Spotify's permission. III.11 asks products to 'add independent value or functionality'. The Spotify mode therefore needs a TwinSpin-specific reason to exist and should not be presented as a Spotify replacement. II.5 says there may be no playback without relevant cover art and metadata. II.4.1 requires Spotify Marks attribution under the Branding Guidelines, and II.4.2 requires links back. VI.2 bans names starting with 'Spot' (the device name 'TwinSpin' is fine).
- **partly-true**: 12. History: Spotify left DJ apps 2020-07-01; returned 2025-09-24 via rekordbox/Serato/djay (Premium, 51 markets); mobile rekordbox/djay 2025-12-11; VirtualDJ/Cross DJ/edjing 2026-09-15; 'licensing and technical agreements'; up to 4 tracks; online only; no stems/offline; personal only; no open partner application.
  - CORRECTION: Dates and partners are confirmed by Spotify's newsroom post and its appended updates. The 2026-09-15 update names 'VirtualDJ, Cross DJ, and Edjing Mix'. The 2020-07-01 exit is confirmed by Algoriddim's announcement as reported by press. Corrections: (a) 'licensing and technical agreements' is DJ TechTools' wording, not Spotify's. (b) 'Up to 4 tracks at once' is contested. Serato's own help centre says Spotify streaming is 'limited to tracks on up to two decks at a time'; the 4-deck figure comes from Serato launch press. Spotify publishes no deck limit. (c) Personal-use-only and no venues or livestreams comes from third-party coverage (e.g. HiResAudio); Spotify's newsroom and dj-integration pages do not state it, though Policy III.10 and the consumer terms imply it. Serato also does not support recording with Spotify tracks. (d) 'No open partner application' is consistent with all sources but cannot be proven; no public programme was found. At launch rekordbox supported only Performance mode.
- **confirmed**: 13. Policy III.10 personal/non-commercial, no public business play; IV.2 'commercial uses are not permitted for SDAs'; IV.1 streaming only for subscribers.
  - CORRECTION: Accurate. The IV.2 lead-in carves out limited commercial use for Non-Streaming SDAs, but TwinSpin with the SDK is a Streaming SDA. IV.2.1–IV.2.3 then specifically ban selling the SDA or access to it, any e-commerce or in-app payment or monetisation initiated via it, and ads, sponsorships or promotions on it. If TwinSpin ever adds ads, a tip jar or paid features, those must not be part of the Spotify-enabled app.
- **partly-true**: 14. Embed iFrame API needs no developer app (loadUri/loadEntity, play, pause, resume, seek, playback_update); full tracks only when logged in to spotify.com with third-party cookies allowed, otherwise 30-s previews; no queue/shuffle/repeat API.
  - CORRECTION: The method and event list is correct. loadEntity is the recommended method; loadUri is legacy 'for existing integrations'. Other methods are togglePlay, restart and destroy, plus playback_started and ready events. There is no queue, shuffle, repeat or next-track API. The docs never mention a client ID, which supports 'no developer app'. The rule that logged-out users get 30-second previews is supported only by community posts and Mozilla's webcompat shim (embeds need first-party storage access to detect login); Spotify's docs do not state it. Several reports say full playback works reliably only on desktop with a logged-in Premium account, and that mobile often stays in preview mode. Embed audio also plays in a cross-origin iframe, so it cannot reach TwinSpin's engine. III.7 (no mixing) applies to it too.
## Extra findings
- MISSED (important for the user's 'Spotify OR Suno' question): Policy III.5 says 'Do not create any product or service which is integrated with streams or content from another service.' If one TwinSpin player integrates both Spotify and Suno (or SoundCloud etc.), it risks breaching III.5. Keep Spotify isolated, and possibly ship it as a separate page or app, or offer only one third-party service. Source: https://developer.spotify.com/policy
- MISSED: Policy III.13 says 'Do not analyze the Spotify Content or the Spotify Service for any purpose'. It independently bans BPM, beat-map, waveform or loudness analysis of Spotify tracks, beyond the technical block. III.14 also bans using Spotify content to train or feed AI/ML models. Source: https://developer.spotify.com/policy
- MISSED: Policy III.6 says 'Do not synchronize any sound recordings with any visual media'. TwinSpin's audio-reactive visualizers or video features must not run on Spotify playback. III.3 bans voice control of Spotify and III.2 bans games or trivia, if TwinSpin has either.
- MISSED: Policy I.1 (Users and Data) requires a privacy policy, minimal data collection and an easy way for users to disconnect and delete their data. Even a static site needs a visible 'Disconnect Spotify' button that clears its localStorage tokens, plus a privacy notice.
- MISSED: The SDK's actual architecture: spotify-player.js injects a hidden iframe from https://sdk.scdn.co/embedded/index.html with allow='encrypted-media; autoplay'. If TwinSpin is ever embedded in an iframe (e.g. inside another page), that outer iframe must also allow encrypted-media and autoplay, per the SDK docs. The bundle supports Widevine, PlayReady and FairPlay. Verified by curl on 2026-10-13.
- MISSED: The Feb 2026 changes removed the 'product' and 'email' fields from the user object, so the app cannot pre-check Premium through GET /me. Detect it with the SDK's account_error event, or a 403 'Premium required' from player endpoints. Users who are not allowlisted get 403s on every API call, so the public GitHub Pages site needs a clear 'this mode is invite-only' message. Source: https://developer.spotify.com/documentation/web-api/references/changes/february-2026, https://developer.spotify.com/documentation/web-api/concepts/quota-modes
- MISSED: Spotify's Feb 2026 blog describes Development Mode as for 'learning, experimentation, and personal projects for non-commercial use by individual developers'. That matches TwinSpin as a personal project, but it reinforces that a Spotify mode can never be a public feature of the GitHub Pages site. In practice it would serve the owner plus up to 4 named friends.
- MISSED: Live CORS check on 2026-10-13. accounts.spotify.com/api/token and api.spotify.com both reflect Origin https://ranama.github.io and allow the needed methods and headers, so a no-backend PKCE flow and Web API calls work from GitHub Pages. The SDK script sdk.scdn.co/spotify-player.js is served with Access-Control-Allow-Origin: *. Note that the client_id will be public in the JS, which is normal for PKCE.
- MISSED: The researcher's 'starting one pauses the other' rule is necessary but may not be sufficient on its own. Policy III.7 bans 'overlap', so any TwinSpin fade-out tail or transition into or out of a Spotify track (e.g. crossfading from a local deck into Spotify) counts as overlap. Switching must be a hard stop.
- MISSED (minor risk): A community thread reports that player.connect() never resolves in Development Mode after the Feb/Mar 2026 changes (title only, unconfirmed): https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-player-connect-never-resolves-in-Development/td-p/7392190. Another reports Lite/Premium Mini accounts failing with account_error even though /me showed product=premium. Budget time for real-device testing.
- POSSIBLE OPTION NOT MENTIONED: GET /tracks/{id} still returns external_ids (ISRC; the removal was reverted in March 2026). A feature that matches a user's Spotify playlist to audio files they already own locally, and then DJs those local files, avoids streaming Spotify audio. It still has to respect III.9 (no transferring data to another service, although playlist-metadata portability is explicitly excepted) and II.4.3 (no standalone metadata service). This needs a careful policy read before building it.
