# verify-bpm
- **partly-true**: 1. Essentia.js is AGPLv3 (also sold under a commercial license) and is about 2.5 MB of WASM plus JS. The TISMIR paper benchmarks a Redmi Note 7 Pro at 0.46-3.48 s per 30 s clip, with Chrome the slowest browser. There are no published rhythm-specific mobile numbers. It is a heavy, licence-encumbered dependency.
  - CORRECTION: The license is correct: the npm license field says AGPL-3.0, and UPF/MTG sells a commercial licence. The size is roughly right. essentia.js@0.1.3 ships essentia-wasm.web.wasm at 1,987,689 B, essentia-wasm.web.js at 220,465 B and essentia.js-core.min.js at 42,959 B, about 2.25 MB uncompressed. The single-file ES build with the WASM embedded, essentia-wasm.es.js, is 2,562,601 B. The benchmark description is wrong. The Redmi Note 7 Pro benchmark (Android 9 LineageOS, Chrome 84 and Firefox Nightly) is in the ISMIR 2020 conference paper, not a TISMIR article. It used a 5-second clip, not 30 s. The paper says Node.js was the slowest environment, followed by the Android browsers, not Chrome. The figures 0.46-3.48 s appear nowhere in the text (results are figure-only) and could not be verified. Rhythm-specific mobile numbers do exist. Joglar-Ongay's 2020 MTG master's thesis benchmarked 'Beats Zapata' and 'Beats/BPM' on the Redmi Note 7 Pro and an iPhone 8 (iOS 13 Safari, Chrome and Firefox Focus), again on 5-s segments and only as plots. It reports iOS times close to desktop and Android 'considerably slower'. iOS runs had to be capped at 5 repetitions because of out-of-memory errors. Also missed: the last npm release is 0.1.3 from 2021-06-24, more than 5 years without a release.
- **partly-true**: 2. Octave errors dominate tempo estimation. In TISMIR 2020, Percival's Acc1 drops to zero above ~150 BPM. On GiantSteps the best Acc1 was only 58.9% (64.8% corrected) vs 86.4-94.0% Acc2, so x2 and /2 buttons plus a range setting are mandatory.
  - CORRECTION: The numbers are right but misattributed. Schreiber, Urbano and Müller, 'Music Tempo Estimation: Are We Done Yet?' (TISMIR 3(1), 2020) give 58.9% to 64.8% ACC1 and 86.4% to 94.0% ACC2 for the böck system, before and after the crowdsourced GiantSteps re-annotation. The paper does not call this the best ACC1 on GiantSteps. 'perc's ACC1 drops to zero for T > 150BPM' is quoted correctly, alongside 'böck's ACC1 sharply decreases to 27.3% or less for T > 190BPM'. The octave-error point holds: errors cluster at -1 tempo octave (half tempo) for all systems except böck, schreiber2017 and schr. Note that ACC2 also counts x3 and /3 as correct. The design conclusion (x2 and /2 buttons plus a range preset) is sound.
- **partly-true**: 3. web-audio-beat-detector: OfflineAudioContext 240 Hz lowpass, channel 0 only; threshold crossings from 0.95*max down to 0.3*max until >=30 peaks, skip 0.25 s; intervals to next 10 peaks folded into 90-180, grouped within ±0.5 BPM; guess() returns bpm=Math.round(tempo), offset = first peak mod beat; README claims only 'surprisingly good results especially for electronic music'; no sub-BPM precision, single-peak offset; unsuitable for DJ sync.
  - CORRECTION: Confirmed from the source: BiquadFilter lowpass at 240 Hz in an OfflineAudioContext (standardized-audio-context); getChannelData(0) only; threshold starts at 0.95*max and drops in 0.05*max steps to 0.3*max until 30 peaks; a skip of sampleRate/4 samples after each peak; the default fold range 90-180 (configurable via minTempo/maxTempo); the README accuracy sentence. Corrections: (a) intervals go to the next 9 peaks, not 10 (loop i=1..min(n-index,10)-1). (b) A 'peak' is the falling-edge crossing (the last sample above threshold), which lands late relative to the onset. (c) If the lowpassed max is <= 0.25, no peaks are searched and it throws 'does not contain any detectable beats', so quiet or low-bass masters fail outright. (d) Buckets merge only exactly equal intervals. Neighbours within ±0.5 BPM add weighted score, but the reported tempo is one integer-sample interval's value, not an average. (e) analyze() resolves with the unrounded tempo, and guess() returns {bpm: Math.round(tempo), offset, tempo}, so a float is available. It is still unrefined (single-interval) precision, not 'no sub-BPM value'. (f) offset = the earliest peak of the winning bucket, reduced by 60/ROUNDED bpm, so it is itself biased by the rounding. The conclusion (rough hint only, unsuitable for a DJ grid) stands. Latest npm version is 8.2.39 (MIT).
- **confirmed**: 4. Grid drift = (ΔBPM/BPM)*elapsed time; <10 ms over 6 min at 128 BPM needs ΔBPM <= 0.0036; integer-rounded BPM on a 127.5 track is 0.39% off, drifting half a beat per minute; keep float64, round only for display.
- **confirmed**: 5. Prototype results (Chrome 152 desktop, synthetic): BPM exact (|err|<=0.0008) on all 16 cases; integer/half snapping works; folded-phase first beat within ±0.4 ms after +2.6 ms calibration (1.6-4.1 ms with tonal pads); noise/pad-only conf 0; 0.5%/2% wobble and 120->124 ramp flagged variable (RMS 33-210 ms vs 1-4 ms).
  - CORRECTION: Reproduced by re-running the researcher's analyzer.js and synth.js unchanged in Chrome 152.0.7977.130 on the same machine. BPM error was ≤0.0008 on all constant-tempo cases, including the claimed cases missing from test.html (126.37 with 10 ms humanize: -0.0004; 127.5 with a 60 s breakdown: snapped to 127.5). Folded-phase error was ≤0.37 ms on drum-only cases, 1.55 ms with the pad intro, and -1.4 ms with 10 ms humanize (so not ±0.4 ms for every case). Noise-only and pad-only gave conf 0. Residual RMS was 33.2 ms (0.5% wobble), 134 ms (2% wobble) and 209.6 ms (ramp), all flagged variable. This holds only for the synthetic set. Off-beat-heavy adversarial cases fail (see extraFindings).
- **confirmed**: 6. Fourier-angle (PLP-style) phase is biased by syncopation: -72 to -103 ms hip-hop, +37 ms half-time dubstep, -18 ms DnB with swing; folding modulo the period (128 bins) fixes it to <0.5 ms; use Fourier phase only for relative tracking.
  - CORRECTION: Reproduced with small numeric differences: Fourier-phase error was -74.7 ms (hip-hop 92 straight), -101.3 and -101.8 ms (hip-hop 88 and 84 with swing), -105.4 ms (hip-hop 80 at -20 dB noise), +34.7 ms (dubstep 140) and -21.0 ms (DnB 176 with swing 0.58). Folded phase was -0.27 to +0.37 ms on the same tracks. The Fourier phase was also biased on non-syncopated material: -4.05 ms with off-beat bass and -8.24 ms with a pad intro. This supports never using it as the absolute anchor.
- **confirmed**: 7. Octave decision from log-compressed flux fails (87 vs 174 DnB, 168 vs 84 hip-hop); folding LINEAR >2.5 kHz energy flux on the fast grid gives rho 0.99-1.0 DnB, 0.07 hip-hop; threshold 0.5 tuned on synthetic only.
  - CORRECTION: Confirmed on synthetic data only. rho from linear high-band flux was 0.99-1.00 for DnB 165/172/174/176, 0.06-0.07 for hip-hop 76/80/84/88, and 0.05 for dubstep. Log flux summed over all bands gave rho 0.12-0.25 on DnB (so it would pick 86/87) and 0.75-0.78 on hip-hop (so it would pick 168). Log flux of the high band alone was also ambiguous: 0.37-0.62 on hip-hop and 0.60 on dubstep. Caveat: the synthetic snare is 1.2x band-passed noise at 2 kHz and the kick click is tiny. Real hip-hop with loud 8th-note open hats, crashes or bright kicks could push rho either way, so the threshold must be re-tuned on real tracks, as the researcher says.
- **partly-true**: 8. Performance: 96 ms for 8-min 48 kHz mono on desktop Chrome 152 (onset 77, ACF 9, zoom 8, phase+fold ~1); 3-min 44.1k 25-70 ms; no FFT; phones assumed 4-8x slower -> 0.4-0.8 s.
  - CORRECTION: The desktop numbers reproduce, and are slightly faster here: 63-69 ms for 8 min at 48 kHz (onset 45-50, ACF 8-11, zoom 8, phase 1, fold 0) and 25-31 ms for 3 min at 44.1 kHz. No FFT is used. The phone figure is an untested assumption: no phone was measured, and the 4-8x factor is unsourced. The timing also leaves out decodeAudioData, which on a phone takes far longer than this analysis for an 8-min MP3, plus the stereo downmix, the postMessage transfer and the Stage-4 octave pass (not run for the 128 BPM perf track). Treat the 2 s budget as unverified on phones until measured on a mid-range Android and an older iPhone.
- **partly-true**: 9. BaseAudioContext (thus OfflineAudioContext/decodeAudioData) and AudioBuffer are [Exposed=Window], so decoding cannot happen inside a Worker; decodeAudioData resamples to the context rate (often 48 kHz on phones); decode on main thread, then send PCM to the worker.
  - CORRECTION: The Web Audio part is correct. webref IDL shows [Exposed=Window] on BaseAudioContext, AudioContext, OfflineAudioContext and AudioBuffer, and the spec says decodeAudioData must 'resample it to the sample-rate of the BaseAudioContext'. However, 'decoding cannot happen inside a Worker' is too strong. WebCodecs AudioDecoder is [Exposed=(Window,DedicatedWorker), SecureContext] and ships in Chrome/Android Chrome 94, Safari/iOS Safari 26 and Firefox 130 desktop (not Firefox Android). It needs your own demuxing (MP3 frame parsing, MP4/M4A boxes, WAV headers), does no resampling, and codec support must be probed with isConfigSupported(). So decodeAudioData on the main thread remains the pragmatic choice. Its decode work is asynchronous and off the main thread anyway; only the resulting AudioBuffer lives on Window.
- **partly-true**: 10. Traktor: x2 and /2 in GRID tab, tapping guides auto-detection, grid lock, default range 78-155 (third-party). Serato: BPM Range setting 58-115/68-135/78-155/88-175/98-195. rekordbox: Normal mode with BPM range, Dynamic mode for drifting tempo, GRID TAP/halve/double/first beat/nudge.
  - CORRECTION: Traktor is confirmed from the current NI manual. The Advanced Panel GRID page has BPM x2 ('Doubles the BPM of the current tempo zone'), BPM /2, TAP ('Refines the BPM based on tapped speed. The BPM will be updated after the fourth tap.'), an Analysis Lock button, Reset BPM and Set Grid Marker. The wording 'current tempo zone' shows Traktor now supports multi-zone (variable-tempo) grids too. The '78-155 default' could not be verified. The Analyze Options page describes the BPM Range as min/max plus an 'Automatic' option that 'uses artificial intelligence techniques', for example keeping DnB at 170 rather than 85. The Serato ranges and rekordbox's Normal/Dynamic modes could not be verified: Serato support returns 403 and the rekordbox 7.2.18 manual PDF could not be text-extracted. Treat both as unverified, not confirmed.
## Extra findings
- CRITICAL, measured: Stage 2 (pair-summed ACF at fps2 ≈ 86-94 Hz, comb A(τ)+A(2τ)+A(4τ) with linear lag interpolation) picks the 3-half-beat (2/3-tempo) level on tracks with strong off-beats. Test: house plus off-beat tonal chord stabs (440-880 Hz, 3 ms attack). It failed for 125 BPM @44.1k, 127 @44.1k (stab gain 1), 124 and 126 @48k, and even the researcher's own houseOffbeatBass pattern at 132 BPM @48k. Outputs were 83.2, 164.5, 168.5 and 174.9 BPM. That is 8 of 66 tempo/sample-rate/pattern combinations, depending on how the beat period lines up with the frame grid. The cause is a frame-quantisation artefact: for 125 BPM house alone, A(3 beats)=0.99 vs A(1 beat)=0.84. With off-beats present, A(1.5 b)=0.91 beats A(1 b)=0.84, so comb(83.3)=2.79 > comb(125)=2.21. All failures came out with conf=0, so the UI would show 'BPM ?' rather than a wrong grid, but they are wrong answers. The correct tempo was always in the top-6 alternatives. Verified fix: run Stage 3a, 3b and 6 for the top 3-4 candidates (folded into range) and keep the one with the best fold contrast x coverage. In the failing cases the correct candidate scored contrast 1.00 and coverage 1.00; the 3:2 candidate scored ≤0.03 and 0.00. Also smooth the OSS (Gaussian σ≈1 frame) or take the max over ±1 lag / a parabolic peak per harmonic, instead of linear interpolation on the decimated ACF. Add 'house with off-beat chord stabs/organ' and 'reggae/ska skank' at many tempos and both sample rates to the unit tests.
- Main-thread chunking recommendation: about 1 s of audio per task means ~480 tasks for 8 min. Per the HTML timer rules, nested setTimeout is clamped to ≥4 ms after 5 levels, which adds ~2 s of latency. Time-slice instead: run until ~8 ms has elapsed, then yield via MessageChannel, or scheduler.yield() where it exists (not universally available; feature-detect). Or process bigger chunks (10-30 s of audio). The downmix itself is ~23-46M float reads, tens of ms on desktop and a few hundred ms on phones.
- latencyBias = 2.6 ms is mostly a hop-alignment bias of roughly H/2, which is 2.9 ms at fsd 11025 and 2.67 ms at 12000, plus the group delay of the cascaded 150 Hz lowpass. Express it in hops, or calibrate per fsd. Measured 44.1k and 48k folded-phase errors agree within ~0.2 ms, so this is minor. The bias is also content-dependent (low-band vs mid-band onsets) by about ±1-2 ms.
- With the [78,156) fold plus Stage 4, slow material at 60-77 BPM (lo-fi, ballads, slow hip-hop at 70-76) is always reported doubled. Measured: hip-hop at 76 came out as 152 with conf 1, which is wrong with high confidence. The range-preset UI (58-115) and the x2 and /2 buttons are needed for this. DnB above 180 folds to 90+, skips Stage 4 and comes out halved.
- Synthetic tests put every hit at exact sample positions on a perfectly periodic grid, which makes the frame-quantisation artefacts larger than in real music. They also cannot show real-world failure modes (sidechained pads, swung UK garage, off-beat organ house, live drummers). The 20-50 real-track regression set is essential before tuning rho, contrast or drift thresholds. Re-run the analyzer on each candidate tempo across both 44.1 and 48 kHz decodes of the same file.
- Memory on iOS Safari: decoded 8-min stereo at 48 kHz is ~184 MB per deck as Float32. Two decks plus the AudioWorklet copy plus analysis copies can pass ~0.5 GB. The 2020 Essentia.js thesis already hit out-of-memory errors on an iPhone 8 (2 GB RAM) in the benchmark loop. Transfer, don't copy, PCM to the worklet; build the 4x-decimated mono analysis copy (23 MB) and release intermediates; avoid structured-clone copies of full-rate channel data.
- Persisting edits and analysis in IndexedDB: in a sandboxed iframe preview without allow-same-origin, IndexedDB/localStorage access throws SecurityError, so wrap it in try/catch. Safari's ITP 7-day cap on script-writable storage can wipe saved grids for a browser-tab site the user hasn't interacted with in 7 days of Safari use; home-screen installed web apps are exempt. Since analysis is cheap, cache user edits rather than raw analysis. Key on name+size+lastModified+decoded length/sampleRate, because MP3 encoder-delay trimming differs between decoders and shifts firstBeat by ~25-50 ms.
- essentia.js has had no npm release since 0.1.3 (2021-06-24). Beyond the AGPL obligations for a hosted web app (the source must be offered to users), that is another reason not to depend on it. As a test-label reference, note that RhythmExtractor2013 needs 44.1 kHz input, so resample first. Essentia's PercivalBpmEstimator takes a sampleRate parameter.
- web-audio-beat-detector edge case worth knowing if it is used as a fallback hint: it throws when the 240 Hz-lowpassed channel-0 peak is ≤0.25, so quiet masters fail. Its default range is 90-180, not the 78-155 DJ convention.
