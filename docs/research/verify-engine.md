# verify-engine
- **partly-true**: 1. Touch scratching: follow finger position with smoothing. GalacTechNyc/djay deck-core.js uses gap->want over ~20 ms, rate += (want-rate)*0.05, cap +/-12, raised-cosine strokes; musudik/DJ-Console sets rate = jog with no smoothing and no declick; pixelputra-cloud/dj-scratch-deck uses an a-rate 'rate' AudioParam -16..16 smoothed with setTargetAtTime. Velocity-only control drifts; unsmoothed 60-120 Hz updates buzz.
  - CORRECTION: GalacTechNyc and pixelputra are described correctly. musudik/DJ-Console is described wrongly. Its worklet does set rate = jog directly (deck-processor.js line 105), but jog is an a-rate AudioParam (-64..64). The main thread drives it with jogParam.setTargetAtTime(v, ctx.currentTime, 0.005) (src/audio/deck.ts line 242), so it is velocity control with a 5 ms smoother, not unsmoothed. It is true that it has no position following and no explicit declick. The drift and buzzing statements are sound DSP reasoning, but no source was found for them.
- **confirmed**: 2. Interpolation cost in Chrome 152 (16 threads): linear 1.17/1.62 ns, Hermite 2.89/4.71 ns, sinc16 19.5/26.2 ns per sample. 192k interp/s for 2 stereo decks gives about 0.55-0.9 ms/s for Hermite and 3.8-5 ms/s for sinc16. At 3-10x slower phones, Hermite stays under about 1% of a core.
- **confirmed**: 3. Over plain http://192.168.x.x AudioWorklet is unavailable because BaseAudioContext.audioWorklet is [SecureContext] (Web Audio 1.1 WD 22 Sep 2026, MDN). HTTPS and localhost qualify. createScriptProcessor is not secure-context gated, is deprecated but still present, and has no removal milestone.
- **partly-true**: 4. Static imports inside AudioWorklet modules: Chrome yes (verified blob importing blob in Chrome 152); Firefox from 113 (bug 1572644, previously 'Module resolve hook not set'); Safari unknown. Ship one self-contained file.
  - CORRECTION: Chrome and Firefox are right. Safari is not unknown. In the 2026-10-06 wpt.fyi stable run, Safari 27.0 passes 18/18 of /worklets/audio-worklet-import.https.html. That file includes 'Importing nested scripts resolves the given promise', which uses a static import, and 'Importing cyclic scripts'. Chrome 154 and Firefox 157 also pass 18/18. The first Safari version with this support is still unverified. The advice to ship one self-contained file with no imports is still sound.
- **confirmed**: 5. addModule with blob: URL works in Chrome 152; WebKit changeset 270046 fixed data: URL worklets; a CSP script-src without blob: blocks blob worklets in Chromium/Firefox; worklet modules are fetched in CORS mode; an opaque sandbox origin needs ACAO even for same-host files; GitHub Pages sends ACAO: *.
- **confirmed**: 6. A source AudioWorkletNode with numberOfInputs: 0 and no outputChannelCount renders mono; outputChannelCount: [2] gives stereo.
- **confirmed**: 7. postMessage with a transfer list is zero-copy. Transferring AudioBuffer.getChannelData(c).buffer works in Chrome 152 and detaches the AudioBuffer channel; Safari and Firefox are unverified. Without a transfer the payload is structured-cloned and deserialized on the audio thread. Heavy onmessage work glitches.
- **partly-true**: 8. iOS silent switch: WebKit defaults Web Audio to AmbientSound (MediaSessionManagerCocoa); navigator.audioSession.type='playback' ignores the switch (jya on bug 237322: from iOS 17). caniuse: Safari/iOS 16.4 and Firefox 160; Chrome no. W3C draft is dated 13 Nov 2024. 'playback' does not mix with other apps.
  - CORRECTION: Everything checks out except Firefox. caniuse shows 'Firefox 160' only because BCD has firefox version_added 'preview'. Firefox 160 is not released: it ships 10 Nov 2026, and the current release on 2026-10-06 is Firefox 157. In practice, only Safari/WebKit (16.4+) supports navigator.audioSession today. jya's actual wording, on 2024-09-25, was 'Since iOS 17, you can set the audio session type to "playback"'. The no-mixing behaviour is defined in the spec; I did not test that it stops Spotify on a device.
- **confirmed**: 9. iOS background/lock: without 'playback' the context is suspended or interrupted. WebKit bug 261554 was fixed March 2024 and confirmed in iOS 17.5; it regressed in 17.2-17.3. With 'playback' on iOS >= 17.5, audio should continue when locked.
- **confirmed**: 10. Android Chrome screen-off: no deliberate WebAudio suspension; Web Audio alone gets no media notification (needs a media element of at least about 5 s); OEM battery killers are possible; mitigate with Wake Lock, optionally a silent looping <audio> plus Media Session.
- **confirmed**: 11. decodeAudioData resamples to ctx.sampleRate and detaches the input. A 6 min stereo track is 127.0 MB (44.1k) or 138.2 MB (48k) as float32, and 63.5/69.1 MB as Int16.
- **partly-true**: 12. Phone memory risk: iOS tab budget is about 1.5-3 GB, and the tab is reloaded when over. Chrome decodeAudioData showed huge peaks (73 MB podcast, 1.9 GB). Android decode is slow; a 9 MB MP3 crashed an old iOS device. Peak during load is roughly encoded + AudioBuffer + any copy.
  - CORRECTION: The risk is real, but the peak estimate is too low for Chrome. Chromium's decode path holds several full-size float copies: decoded packets (a vector of AudioBus), the assembled AudioBus, a second resampled AudioBus when the file rate differs from the context rate (for example 44.1 kHz into 48 kHz), and the AudioBuffer built from it. Peak can therefore be about 3-4x the final float size plus the encoded bytes. A 6 min 44.1 kHz track decoded into a 48 kHz context can transiently need about 400-550 MB. The 73 MB/1.9 GB and 9 MB MP3 reports were not verified. iOS jetsam at over 1.5 GB is documented, and it is made worse by back-to-back decodes.
- **partly-true**: 13. decodeAudioData format matrix: MP3 all; AAC/M4A Chrome + Safari, Firefox via OS; ALAC Safari only; FLAC Chrome 56+/Firefox 51+/Safari 11+; WAV 16/24/32f in Chrome and Safari, Firefox likely; AIFF Safari only; Ogg in Chrome and Firefox, Safari 18.4 added Ogg; WebM Opus decode in Safari fixed 2021; Opus-in-MP4 fixed in Safari 27.0; CAF Opus Safari only.
  - CORRECTION: Most entries are correct. Corrections: (a) Firefox WAV is confirmed in source, not just likely. Its FFmpeg path maps 8/16/24/32-bit integer PCM and 32-bit float (codecs=3), plus a-law and mu-law. Chrome's allowed decoders are pcm_u8, s16le, s24le, s32le, f32le, s16be, s24be, mulaw and alaw; there is no 64-bit float. (b) Chrome's allowed demuxers are ogg, matroska, wav, flac, mp3, mov and aac, with no AIFF and no ALAC decoder, which confirms the AIFF and ALAC rows. (c) WebM Opus decodeAudioData in Safari worked on macOS 12.3 and iPadOS 15.4 in 2022, but only became consistent on iPhone iOS around Safari 17.4 (per a user comment), so '2021' is too early for phones. (d) Safari 18.4 added Ogg Opus and Vorbis on macOS 15.4/iOS 18.4. WebKit main maps 'Oggf' to audio/ogg in its AVURLAsset-based decoder, but decodeAudioData Ogg on iOS 18.4 is still unverified on a device. (e) New: Safari 27 has a regression where decodeAudioData silently truncates ALAC input larger than about 32 MB (WebKit bug 325481, 2026-09-28). (f) The 'full macOS 13+' FLAC note was not verified.
- **partly-true**: 14. iOS hardware usually runs at 48 kHz. iOS 9-14 had distortion when context and hardware rates mismatched, reportedly fixed by iOS 15. Do not force sampleRate. Safari 26.0 fixed stale audio buffer data after seeking through an AudioContext.
  - CORRECTION: The Safari 26.0 fix is confirmed, but its release note is in the Media section and most likely concerns media elements routed through an AudioContext, not decoded-PCM worklets. Rate-change distortion is documented for iOS 9.2-10.2 (WebKit bug 154538, fixed r198035 in March 2016). A related bug, 168165, where playing a low-sample-rate video makes all later AudioContexts in the tab inherit that low rate, is still NEW (last modified 2022). 'Fixed by iOS 15' is unverified. 'Do not force sampleRate' is sound advice.
## Extra findings
- The main user requirement (master on one Bluetooth device, cue on another) cannot be met by a browser on a phone today. HTMLMediaElement.setSinkId is not available on Chrome Android or Firefox Android: BCD says 'Not available due to a limitation in Android' (crbug 41276355, bugzil.la 1473346), and Chromium's AudioOutputDevices flag is disabled on Android. Safari 18.4's speaker selection is macOS only: the WebKit 18.4 blog says 'adds speaker selection API on macOS'. BCD's safari_ios 'mirror' entry is misleading. AudioContext.setSinkId exists in Chrome 110 (desktop), with no Firefox or Safari support. Firefox has selectAudioOutput (116, desktop only). On phones, only split-mono mode (a) works, and only into a single stereo device. Modes (b) and (c) work on desktop Chrome/Edge/Firefox, and (b) also on macOS Safari 18.4+ after microphone permission. The UI should state this clearly. Sources: https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/HTMLMediaElement.json and https://webkit.org/blog/16574/webkit-features-in-safari-18-4/
- BiquadFilterNode Q is in dB for 'lowpass' and 'highpass' (spec: alpha_QdB = sin(w0)/(2*10^(Q/20))). A Linkwitz-Riley isolator therefore needs Q = -3.0103 (dB) for a Butterworth response, not 0.7071. In Chromium 152 I measured the 250 Hz / 2.5 kHz LR4 3-band sum: with Q = -3.0103 it stays within -0.11..0.00 dB, which is flat enough without allpass compensation. With Q = 0.7071 it shows a bump of up to +7.5 dB. The 'filter knob Q 0.7-1.0' values are also in dB (about 1.08-1.12 linear).
- DynamicsCompressorNode is not a brickwall limiter, and it applies automatic makeup gain (spec: 'Computing the makeup gain', the 0.6 power of the inverse full-range gain). I measured these settings (threshold -2, knee 0, ratio 20) in Chromium 152. A -20 dBFS sine comes out at -18.86 dBFS (+1.14 dB makeup). A 0 dBFS sine comes out at -0.70 dBFS, and +6 dBFS comes out at -0.28 dBFS. Very large overs could still exceed 0 dBFS. The first output sample was at index 289 at 48 kHz, which confirms the roughly 6 ms look-ahead delay.
- AudioParam float32 precision fails much earlier than 2^24 samples. At around 2^20 samples (about 22 s at 48 kHz) the sub-sample resolution is already only 1/8 sample, which matters for interpolation. This strengthens the 'positions only via postMessage as float64' rule.
- Keep-alive <audio> on iOS: per WebKit bug 168165 (still NEW), low-sample-rate media can push later AudioContexts in the tab to that low rate. Generate the silent WAV at 48000 Hz, or at ctx.sampleRate, never at 8 or 22.05 kHz to save bytes. Per WebKit's MediaSessionManagerCocoa, any audible media element switches the category to MediaPlayback, which ignores the mute switch. That is why the trick works, and also why it stops other apps' audio.
- WebKit ignores latencyHint: AudioContext.cpp has '// FIXME: Figure out where latencyHint should go.'. MediaSessionManagerCocoa also forces the preferred IO buffer to renderQuantumSize (128 frames) whenever Web Audio is active. A 'Stable audio' mode cannot help on iOS, so the worklet CPU budget must stay small there. Chromium's WebAudioBypassOutputBuffering is stable only on Win/Mac/Linux/ChromeOS, not Android, so Android latency is higher.
- The 'Stable audio' recommendation (recreate the context) conflicts with two other recommendations. 'Never call close()': the old context must be closed or it keeps the audio device. 'Only one PCM copy, transferred to the worklet': after a transfer, the main thread no longer has the PCM, so the old worklet must post its buffers back (transfer again) before the context is replaced, or the tracks have to be decoded again.
- Safari 27 regression (WebKit bug 325481, 2026-09-28): decodeAudioData silently truncates ALAC input larger than about 32 MB and throws no error. Compare the decoded duration with the expected duration (for example from an <audio> element's metadata) and warn the user.
- Decode one file at a time. WebKit bug 227636 shows back-to-back decodeAudioData calls can push iOS over the 1.5 GB jetsam limit, and Chromium keeps several full-size copies while decoding. For very long tracks, WebCodecs AudioDecoder (Chrome 94, Firefox 130 desktop, Safari 26) can decode in chunks straight to Int16 with a much lower peak, but it needs JS demuxing.
- When converting to Int16, clamp to [-1, 1). Decoded MP3/AAC often has inter-sample peaks above 1.0, and an unclamped conversion wraps around and clicks.
- User activation: pointerdown with a touch pointer is not an activation-triggering event. Only pointerup (non-mouse), touchend, mousedown and keydown count (https://html.spec.whatwg.org/multipage/interaction.html#activation-triggering-input-event). The first touch-down on a platter therefore cannot unlock audio. Unlock the context earlier with a start overlay or the load/play button.
- Screen Wake Lock: BCD shows iOS 16.4-18.3 as partial; it did not work in Home Screen web apps until iOS 18.4 (WebKit bug 254545; the Safari 18.4 notes say 'Fixed Screen Wake Lock API for Home Screen Web Apps'). Chrome supports it from 84 and Firefox from 126.
- Diagnostics: AudioContext.playbackStats (AudioPlaybackStats, which reports underruns and glitches) ships in Chrome 146+ and is in the Web Audio 1.1 WD, but Firefox and Safari do not have it. outputLatency exists only from Safari 18.4 (Chrome 102, Firefox 70). getOutputTimestamp exists from Safari 14.1. Feature-detect each one.
- The 'interrupted' AudioContextState is now in the Web Audio 1.1 WD, and Chromium implements it: resume() fails with 'Cannot resume an interrupted AudioContext'. In Chromium it currently triggers only when an embedder disables the 'media-playback-while-not-visible' Permissions Policy (stable flag), which matters for iframe previews. Handle 'interrupted' for every engine, not only Safari.
- renderSizeHint: chromestatus feature 5078190552907776 lists desktop_first and android_first as 153 for shipping. It is not exposed in Chromium 152 (I tested: 'renderQuantumSize' in BaseAudioContext.prototype is false). With a larger render quantum, the minimum delay inside a feedback cycle grows beyond 2.67 ms. That is 2.9 ms at 44.1 kHz even with 128 frames. The flanger's base delay minus its depth must stay above that minimum, or the delay is clamped.
- Firefox does not support AudioParam.automationRate (BCD false, bug 1504984). Setting it creates an expando and does not throw, so the try/catch never fires. That is harmless.
- The researcher's 'Chrome 152 on Windows' is the Chromium 152 embedded in Claude Desktop (UA 'Claude/2.19675.1 Chrome/152.0.7977.130'), not Google Chrome stable. The release cadence has changed: Chrome 152 stable on 2026-08-25, 153 on 2026-09-08, and wpt.fyi stable on 2026-10-06 is Chrome 154. Firefox 157 is current and Safari 27.0 is stable. Re-test on real Android Chrome and iOS Safari.
- Because decodeAudioData detaches its input, any retry or fallback decode path needs ab.slice(0) made beforehand. That adds a full copy of the encoded file to peak memory, so do it only for small files.
