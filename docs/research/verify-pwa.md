# verify-pwa
- **confirmed**: 1. [SecureContext] list (audioWorklet, AudioWorklet, AudioWorkletNode, AudioContext.setSinkId/sinkId, HTMLMediaElement.setSinkId, navigator.mediaDevices, serviceWorker, caches, wakeLock, clipboard, storage, File System Access) vs. ungated (AudioContext, decodeAudioData, ScriptProcessor, IndexedDB, localStorage, input file, Fullscreen, vibrate, screen.orientation, mediaSession, audioSession)
- **confirmed**: 2. http://192.168.x.x is not a secure context, so AudioWorklet, SW/Cache, wakeLock and mediaDevices are missing. Only localhost/127.0.0.1 are exempt. Chrome desktop and Android have the unsafely-treat-insecure-origin-as-secure flag; iOS Safari has no override.
  - CORRECTION: The exemption list is slightly wider than stated: 127.0.0.0/8, [::1], localhost and *.localhost (Chrome) are potentially trustworthy, plus file: depending on the UA. Whether the engine 'silently' falls back to ScriptProcessor depends on the app's own feature test. I found no iOS override flag, but that is absence of evidence.
- **confirmed**: 3. Two simultaneous outputs (master to BT speaker, cue to BT headphones) cannot be done from a browser on Android or iPhone. Desktop Chrome/Edge 110+ can do it via AudioContext.setSinkId, Firefox 116+ and Safari macOS 18.4+ via HTMLMediaElement.setSinkId.
- **partly-true**: 4. In a sandboxed iframe without allow-same-origin: localStorage and IndexedDB throw, navigator.serviceWorker throws SecurityError in Chromium, and module/worklet fetches become CORS requests with Origin: null. Programmatic input.click() is refused in sandboxed previews while a <label> works.
  - CORRECTION: The storage, service worker and CORS parts are right. In Chromium the window.indexedDB getter does not throw; indexedDB.open() throws SecurityError 'Access to the IndexedDB API is denied in this context.' The navigator.serviceWorker getter throws 'Service worker is disabled because the context is sandboxed and lacks the allow-same-origin flag.' A feature test with 'serviceWorker' in navigator is safe, but the register() call must sit in try/catch. GitHub Pages sends Access-Control-Allow-Origin: *, so module and worklet loads still work from an opaque origin. Chromium's file input has no sandbox check, only a transient-activation check ('File chooser dialog can only be shown with a user activation.'). The 'sandbox refuses input.click()' part is unverified. The real cross-engine pitfall is WebKit's context-based gesture: any await before input.click() breaks it on iOS.
- **partly-true**: 5. iOS needs navigator.audioSession.type='playback' (Safari 16.4+, not Chrome). Otherwise Web Audio uses the ambient category, is muted by the silent switch and is suspended/interrupted in background. With 'playback', background/lock playback works since iOS 17.5 (WebKit 261554, fixed 2024-03-01, regressed in 17.2-17.3).
  - CORRECTION: The core is correct, but 'works since 17.5' is too clean. More regressions were filed after it: 275603 'REGRESSION (iOS 17.5.1): AudioContext fails to resume after browser tab is minimized and then restored', 276016 'REGRESSION (iOS 17.4.1 - 17.5.1): Web Audio sounds stop playing after losing focus', and 291892, where the AudioContext is silent in a PWA after background while state reports 'running' (iOS 18 to 26.1, reported fixed in 26.2 beta 3). Also, navigator.audioSession.state and onstatechange are NOT shipped in Safari (BCD false, behind WebKit's DOMAudioSessionFullEnabled setting). Only .type works. Ambient muting only applies while Web Audio is the only audible source: an audible media element switches WebKit to MediaPlayback.
- **partly-true**: 6. On Android Chrome an audible tab keeps rendering Web Audio with the screen off or the app switched, rAF stops, timers are throttled, and OEM battery optimisation can kill it.
  - CORRECTION: Documented: hidden pages get no rAF; timers are throttled, and intensive throttling only applies after 5 min hidden AND 30 s of silence; pages playing audio are not frozen or discarded 'unless under extreme resource constraints'. Those docs are platform-generic, mostly about desktop tabs. I found no primary source specific to Android screen-off behaviour for Web Audio-only pages, or to whether Chrome Android shows a media notification (foreground service) for Web Audio without a media element. The OEM-kill part is plausible but unverified.
- **partly-true**: 7. iOS 26 Home Screen web apps have audio regressions (26.0.1: resume() fails with 'InvalidStateError: Failed to start the audio device'; playback stops when locked); the same pages work in a Safari tab. WebKit 198277 was fixed in iOS 15.4.
  - CORRECTION: iOS 26 PWA audio regressions are real and filed. WebKit 295518 'REGRESSION (iOS 26): Audio Element Fails to Play on Reopen in PWA': play() resolves with no sound, still NEW, confirmed through 26.1 beta 2. WebKit 291892: Web Audio is silent after a PWA returns from background and resume() can hang (iOS 18 to 26.x; a user reports it fixed in 26.2 beta 3). I could not find the exact 'InvalidStateError: Failed to start the audio device' string in WebKit Bugzilla. 198277 is RESOLVED DUPLICATE of 232909, and the fix shipped in iOS 15.4.
- **partly-true**: 8. On iOS a bare accept='audio/*' greys out .m4a (and reportedly .mp3); listing explicit MIME types and extensions with audio/* last fixes it (Gradio PR #4071). Apple Music/streaming tracks cannot be reached.
  - CORRECTION: The documented mechanism is different and the effect is worse. WebKit maps audio/* to UTTypeMovie, so the picker is filtered as if accept='video/*' and excludes .mp3, .wav and .m4a (WebKit 242110, iOS 15, still NEW). iOS also always shows a 'Photo Library / Take Video / Choose File' sheet (WebKit 234566). The Gradio PR confirms the explicit list works on iPhone (merged 2023-05-09), but it is a 2023 data point. The Apple Music/DRM part is plausible, but I found no primary source for it.
- **partly-true**: 9. Per the HTML spec, pointerdown only counts as activation for pointerType 'mouse'; on touch only pointerup/touchend (and click) do. resume(), requestFullscreen, file pickers and vibrate called from a touch pointerdown can fail.
  - CORRECTION: The spec list is correct, but 'click' is not itself activation-triggering. It runs inside the transient activation created by the preceding pointerup/touchend. Chrome's autoplay check for AudioContext uses STICKY activation of the frame or any ancestor, and so does vibrate (it returns false only before any tap). So in Chrome, resume() and vibrate from pointerdown fail only on the very first interaction. Fullscreen and file pickers need transient activation and are the real risk. WebKit uses a context-based gesture model (WebKit 234566), so on iOS do this work synchronously inside the click/touchend handler.
- **partly-true**: 10. svh/lvh/dvh in Safari 15.4, Chrome 108, Firefox 101. Safari 26 ignores theme-color and manifest theme_color for toolbar tint and samples fixed/sticky elements near the edges or the body background. Set explicit html/body background. viewport-fit=cover plus env(safe-area-inset-*).
  - CORRECTION: The unit versions are confirmed. For Safari 26 browser tabs, theme-color is not used and the tint comes from solid background colours of fixed/sticky elements near the edges (WebKit engineer statement in 301756). The sampling breaks if the viewport-covering fixed layer uses only a gradient (325446) or a top bar has backdrop-filter (319479). The claim that manifest theme_color is ignored is unverified, and for Home Screen web apps theme-color is still read at launch. New iOS 27 regression (WebKit 325807, 2026-09-30): standalone web apps can no longer draw under the status bar (black-translucent plus viewport-fit=cover stops working), and runtime theme-color changes are ignored.
- **partly-true**: 11. navigator.vibrate is Chrome Android 32+ only (user activation since 60, blocked in cross-origin iframes), was removed in Firefox 129, and was never in Safari. The iOS <input switch> haptic hack (17.4-26.4) was patched in iOS 26.5.
  - CORRECTION: Chrome Android 32+ is confirmed. Cross-origin iframes have been blocked since Chrome 55, and a user gesture has been required since Chrome 60. Firefox desktop removed it in 129. Firefox Android has been a no-op since 79 (returns true but never vibrates). Safari has never shipped it; WebKit bug 288846 proposes a permission-gated Device Vibration API, but it is unshipped. I could not verify the claim that the switch haptic hack was patched in iOS 26.5: the Safari 26.4/26.5 release notes and WebKit Bugzilla do not mention it.
- **confirmed**: 12. Safari 27.0 (2026-09-17) adds Service Worker static routing (Chrome 123+) and fixes background playlist advance; nothing for iPhone element fullscreen, orientation lock, iOS setSinkId or Vibration.
## Extra findings
- MANIFEST BUG: with "display":"fullscreen", Android Chrome matches (display-mode: fullscreen), NOT standalone. The probe and INSTALL UX check matchMedia('(display-mode: standalone)') || navigator.standalone, so they will treat an installed Android app as not installed. Check fullscreen OR standalone OR minimal-ui. BCD: Safari supports neither display:fullscreen nor display_override (it falls back to standalone) and ignores the manifest 'orientation' member.
- DUAL-OUTPUT GATING BUG: 'setSinkId' in AudioContext.prototype is TRUE on Chrome Android 110+ (chromestatus 5190163462881280). The proposed gate would therefore call getUserMedia({audio:true}) on Android phones. That triggers a mic prompt and moves Android to its system-wide 'communication device' mode (Chromium audio_manager_android.cc), and enumeration still returns only 'default'. On iOS, mic capture switches WebKit to PlayAndRecord/VideoChat (MediaSessionManagerCocoa.mm), which drops BT headphones to the hands-free profile and lowers other audio (WebKit 236219). Never auto-call getUserMedia: show a desktop-only 'Set up second output' button. On Firefox desktop use navigator.mediaDevices.selectAudioOutput() (Firefox 116+, not in Chrome: crbug 372214870 'In development'), which needs no mic permission.
- Two AudioContexts cannot share nodes and run on independent device clocks, so the plan 'master context + cue context each with setSinkId' means duplicating both deck worklets per context and fighting drift. Simpler and works on Chrome 49+, Firefox 116+ and Safari macOS 18.4+: ONE AudioContext; route the cue bus through MediaStreamAudioDestinationNode into an <audio> element with setSinkId(headphonesId). Optionally put the master on AudioContext.setSinkId in Chrome only (Safari and Firefox lack AudioContext.setSinkId; WebKit AudioContext.idl has no sinkId).
- Bluetooth latency: a BT speaker and BT headphones each add their own (different) output latency, so the cue in the headphones and the master on the speaker will be audibly offset, and scratching over BT will lag. Expose AudioContext.outputLatency (Chrome 102, Firefox 70, Safari 18.4 per BCD) where available and add a manual 'cue offset' slider. Set expectations in the UI.
- iOS state reporting is unreliable, so do not drive the 'Tap to resume' overlay only from statechange. WebKit 283419: the context stays 'running' when another app plays. WebKit 291892: 'running' but silent in a PWA after background (iOS 18 to 26.1). WebKit 263627 and 281955: not resumed on foreground. WebKit 323104 (filed 2026-09-01): all audio in a tab dies while every API reports success. Add an always-available 'Restart audio' button that closes and rebuilds the AudioContext and worklets. This needs the PCM, or the compressed Blob for re-decoding, to still be available on the main thread, so transferring the only PCM copy into the worklet conflicts with recovery.
- Chrome 136+ also ships the AudioContext 'interrupted' state on desktop and Android (chromestatus 5172068166139904), so the interrupted handling is cross-browser, not Safari-only. navigator.audioSession.state and onstatechange are not shipped in Safari (BCD false), so only audioSession.type can be used.
- Memory: decoded PCM costs 48000 x 2 ch x 4 B = 384 KB/s, about 23 MB per minute per deck. A 6-minute track is about 138 MB; two decks plus transient AudioBuffer copies during decode and transfer can exceed 400 MB, which risks a tab reload on iPhones. Consider storing PCM as Int16 in the worklet (half the size). Release AudioBuffer references right after transfer.
- Spec details for the PCM plan: decodeAudioData DETACHES its input ArrayBuffer (Web Audio 'Detach the audioData ArrayBuffer'), so keep the File/Blob or slice() a copy if you need the bytes later. Transferring getChannelData() buffers is allowed but leaves the AudioBuffer zero-length ('acquire the content' step 1), so run BPM and waveform analysis before transferring.
- Safari before 27 had broken top-level await and module evaluation order in its ESM loader ('Cannot access ... before initialization', wrong execution order; WebKit blog 'Fixing Top-Level Await in Safari', 2026-09-02). This is a no-build native-ES-modules app and most iPhones run Safari 26 or earlier, so avoid top-level await and circular imports.
- Safari 26/27 tint and status bar: the fixed full-viewport app root must paint a solid background-color, not only a gradient (WebKit 325446). Do not put backdrop-filter on a fixed top bar (WebKit 319479). iOS 27 standalone apps can no longer draw under the status bar and ignore runtime theme-color changes (WebKit 325807, 2026-09-30), so black-translucent plus viewport-fit=cover will not give edge-to-edge on iOS 27. Lay out with env(safe-area-inset-top) and a fallback, and test on iOS 27.
- Storage on Safari: persist() is granted by heuristics, 'like whether the website is opened as a Home Screen Web App' (WebKit 'Updates to Storage Policy', Safari 17). Non-installed tabs remain subject to ITP eviction when the site has not been interacted with for some time. Expect the track library to vanish in a plain Safari tab and tell users to install. Also, every cloudflared quick tunnel run is a NEW origin, so each phone test session starts with an empty library and a fresh SW registration.
- iPad fullscreen: Element.requestFullscreen on iPadOS (16.4 unprefixed) shows an overlay button that cannot be disabled, and 'Swiping down exits fullscreen mode' (BCD). With vertical faders and platter gestures that is fragile, so consider not offering it on iPad, or warn.
- Sandboxed or embedded previews: navigator.serviceWorker throws on access (not on an 'in' check), localStorage throws, and indexedDB.open() throws SecurityError, so wrap SW registration and localStorage in try/catch too, not just IndexedDB. Wake Lock needs allow="screen-wake-lock" and fullscreen needs allow="fullscreen" on the embedding iframe.
- Android Chrome media notification and lock-screen controls are only documented for <audio>/<video> playback of 5 s or longer (web.dev), so Web Audio-only playback may show no notification. If background survival or lock-screen controls matter, test it. Routing the master through MediaStreamAudioDestinationNode into an <audio> element is the usual workaround, at a latency cost (unverified for current Chrome).
- Chromium Android main now has kAAudioPerStreamDeviceSelection (enabled by default but limited to is_desktop() Android devices), so future Android desktop/PC form factors may enumerate real outputs. Detect dual output by enumerateDevices() count, not by user agent.
- Tooling check: the reference tools/serve.ps1 binds only 'http://localhost:<port>/' (HttpListener rejects other Host headers, which is why the --http-host-header localhost:8090 flag for cloudflared is necessary and correct). Its MIME map has no .mjs, .m4a, .flac or .woff2, so .mjs modules would be served as application/octet-stream and fail the strict module MIME check. Use .js or extend the map. publish-web.ps1 has no __BUILD__ replacement today; it needs adding.
- GitHub Pages serves Cache-Control: max-age=600 and Access-Control-Allow-Origin: * (verified with curl). SW update checks bypass the HTTP cache for sw.js by default, but in-page module fetches can be up to 10 min stale, so keeping cache:'reload' in install and cache:'no-cache' in network-first is the right call.
- iOS 26 changed Home Screen behaviour: every site added to the Home Screen opens as a web app by default, with no manifest needed (WebKit Safari 26.0 post). Avoid speechSynthesis anywhere in the app: WebKit 325274 'REGRESSION (iOS 27): Web Speech (speechSynthesis) silences Web Audio (AudioContext) for the rest of the page session' (2026-09-25).
