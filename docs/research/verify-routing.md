- **confirmed**: 2. - **confirmed**: 3. Safari iOS/iPadOS 18.4+ exposes HTMLMediaElement.setSinkId (IDL gated by ExposeSpeakersEnabled & PerElementSpeakerSelectionEnabled, true for PLATFORM(COCOA)); BCD lists iOS 18.4; WebKit 18.4 notes say 'on macOS'; iOS speaker preference is session-wide (AVAudioSessionCaptureDeviceManager::setPreferredSpeakerID); BCD issue #23148 reports 0 audiooutput on iOS; two simultaneous outputs impossible on iOS.
- **confirmed**: 4. Safari's HTMLMediaElement.setSinkId requires a user gesture (SpeakerSelectionRequiresUserGesture default true; NotAllowedError 'A user gesture is required'); unknown deviceId -> NotFoundError; MediaStream-backed <audio> supports output switching via MediaPlayerPrivateMediaStreamAVFObjC::audioOutputDeviceChanged.
- **confirmed**: 5. Chrome/Edge enumerateDevices: without permission at most one entry per kind with empty deviceId/label/groupId; outputs fully listed when (mic permission granted [content setting, no stream needed] AND microphone policy) OR (speaker-selection permission AND speaker-selection policy) [only via unshipped selectAudioOutput]; Windows adds 'default' and 'communications'; Android phones only 'default'.
- **partly-true**: 6. 'speaker-selection' default allowlist 'self'; Chrome AudioContext.setSinkId checks the policy before anything else (NotAllowedError 'Permissions-Policy disallows speaker selection.'), even for ''/{type:'none'}; HTMLMediaElement.setSinkId also rejects and enumerateDevices omits outputs; a cross-origin/sandboxed iframe without allow= cannot do dual output; must run top-level on HTTPS; GitHub Pages fine.
  - CORRECTION: Default allowlist 'self' is right (spec and Chromium). Chrome's AudioContext.setSinkId checks the policy AFTER the detached-document and closed-context InvalidStateError checks, and before resolving any sink, so it applies to '' and {type:'none'} as well. Chrome's HTMLMediaElement.setSinkId does NOT check speaker-selection in the renderer. setSinkId('') or 'default' needs no authorization. For a non-default id, the browser runs the output-permission check (mic permission + microphone policy, OR speaker-selection permission + policy). If it fails, the promise rejects with SecurityError 'No permission to use requested device', not NotAllowedError. enumerateDevices without permission still returns one masked audiooutput entry rather than omitting outputs. In Chrome, a cross-origin iframe with only allow="microphone" (and a mic grant) can list outputs and route an <audio> cue element. Only AudioContext.setSinkId would be blocked there. Safari and Firefox drop speakers when speaker-selection is disallowed, and Safari has a microphone-policy quirk. Practical conclusion: run top-level or same-origin on HTTPS. GitHub Pages sends no Permissions-Policy header, so this is fine.
- **confirmed**: 7. Windows Bluetooth endpoints: Win10 up to 3 endpoints ('{Name} Stereo' A2DP, '{Name} Hands-Free' out+in), opening Hands-Free discards Stereo audio; Win11 unifies to one output + one input, switches to HFP when any app opens the mic or a Communications-category stream, switches back to A2DP 'momentarily' when mic closes; so getUserMedia on a BT headset mic drops it to mono 8/16 kHz until stopped.
- **confirmed**: 8. Chrome Android getUserMedia with default (effects) constraints sets MODE_IN_COMMUNICATION (call-style routing/volume, may use BT SCO); normal mode restored only when no input streams remain; mic permission gives no extra output routing on phones, so never call getUserMedia there.
- **confirmed**: 9. iOS Safari getUserMedia switches the audio session to play-and-record (call-like); BT output goes to HFP quality or the route changes (sometimes speaker); no second-output capability; avoid gUM on iOS; set navigator.audioSession.type='playback' (Safari 16.4+) so Web Audio ignores the silent switch.
- **partly-true**: 10.   - CORRECTION: Windows 11 Shared audio is confirmed: Insider build 26220.7051 (Dev and Beta, 2025-10-31), Copilot+ PCs, Bluetooth LE Audio broadcast, two accessories sharing the same audio. A macOS Multi-Output Device MIRRORS one stream to every device in the stack, so it is not the mechanism for a separate cue. It only hints that two BT outputs can be active at once. Apple's doc does not mention Bluetooth. For split cue, each BT device must be targeted individually as its own CoreAudio device. The 'stutter is common with two Classic-BT sinks' statement is anecdotal and unverified. 'Wired/USB + BT is the reliable combination' is reasonable advice but not sourced.
- **partly-true**: 11. Android: no user-facing way to send DIFFERENT audio from one app to two BT devices; Samsung Dual Audio, Android 16 'Audio sharing' (LE Audio/Auracast, Pixel 8+, Sep 2025) mirror; AOSP combined audio device routing (Android 12+) privileged-only and same stream; native apps can use AudioTrack.setPreferredDevice; Chrome only uses per-stream selection on desktop-form-factor Android; a web page on an Android phone gets exactly one output.
  - CORRECTION: The conclusion is verified from Chromium source: a web page on an Android phone gets exactly one output device, because there is no per-stream selection unless is_desktop(). Combined audio device routing is confirmed: Android 12, privileged system APIs setPreferredDevicesForStrategy etc. The specifics of Android 16 'Audio sharing' (Pixel 8+, rolled out Sep 2025) and of Samsung Dual Audio could not be verified from primary sources here. - **confirmed**: 12. destination.maxChannelCount: Chrome Android defaults to Stereo (only automotive kUseAudioManagerMaxChannelLayout gives more) so expect 2; Safari iOS returns AVAudioSession.maximumOutputNumberOfChannels (4-out interface can report 4, hardware rendering unverified); Safari macOS default device stream configuration; Chrome desktop sink channel count; Windows USB DJ interfaces often expose separate stereo endpoints.

## Extra findings
- CHROME: STORED IDS NEED A LIVE PERMISSION. Every non-default sink (both <audio>.setSinkId and AudioContext.setSinkId) re-runs the output-permission check when it is called: mic grant + microphone policy, or speaker-selection. If the user chose a one-time 'Allow this time' grant, or later revoked the mic, the ids saved in localStorage stop working. <audio> rejects with SecurityError 'No permission to use requested device'. AudioContext rejects with NotAllowedError '...access to the device X is not permitted.' and can also reject with TimeoutError. The researcher's error list (NotAllowedError, NotFoundError, AbortError, InvalidStateError) is missing SecurityError, TimeoutError and NotSupportedError. Sources: html_media_element_audio_output_device.cc, audio_context.cc, audio_output_authorization_handler.cc (chromium main).
- SAFARI macOS: SPEAKERS NEED A MIC GRANT ON EVERY PAGE LOAD. WebKit exposes speakers only if getUserMedia audio was granted to this frame in the current page load (m_grantedAudioFrames is cleared on navigation and reload; UserMediaPermissionRequestManagerProxy::computeFilteredDeviceList). So Safari needs getUserMedia({audio:true}) again after every reload. A stored permission is not enough, unlike Chrome. setSinkId(id) also fails with NotFoundError unless enumerateDevices() has exposed that id in this document (deviceIdToPersistentId map). Useful detail: WebKit carries the click's user-gesture token into the enumerateDevices() resolution (MediaOnly scope). So calling enumerateDevices().then(() => el.setSinkId(id)) from a click handler satisfies the gesture requirement. That fixes the conflict with the researcher's advice to call setSinkId synchronously before any await, which would hit NotFoundError on a fresh load.
- FIREFOX: EXPOSURE IS PER DOCUMENT TOO. Audio outputs are listed only if getUserMedia with audio succeeded in this document (mCanExposeMicrophoneInfo), or selectAudioOutput granted that device in this document (mExplicitlyGrantedAudioOutputRawIds). After a reload, saved ids must go through selectAudioOutput({deviceId}) again (it may skip the prompt), or through getUserMedia (MDN). Firefox enumerateDevices() only resolves while the document has focus (bug 1818588), which matters for devicechange handlers. selectAudioOutput is desktop-only (firefox_android false) and needs transient activation (InvalidStateError otherwise). Firefox has no AudioContext.setSinkId, so the master follows the OS default. Picking a SPEAKER there is pointless unless master is also sent through its own MediaStreamDestination -> <audio>.setSinkId. That option gives both outputs the same pipeline latency. Sources: https://github.com/mozilla-firefox/firefox/blob/main/dom/media/MediaDevices.cpp, https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/selectAudioOutput
- iOS: AUDIOSESSION TYPE NEEDS THE MICROPHONE POLICY. WebKit's DOMAudioSession::setType silently does nothing unless the document is allowed the 'microphone' Permissions-Policy. Inside a cross-origin or sandboxed iframe preview without allow="microphone", navigator.audioSession.type='playback' is ignored. Web Audio alone then gets the Ambient category, which the ring/silent switch mutes. Top-level pages on GitHub Pages are fine because 'self' is the default.
- iOS: getUserMedia DAMAGE OUTLASTS THE STREAM. The PlayAndRecord/VideoChat category stays in place after capture stops for as long as Web Audio keeps playing (MediaSessionManagerCocoa: 'isPlayingAudio && category()==PlayAndRecord'). Stopping the tracks right away does not undo the Bluetooth HFP or speaker route change. This makes the rule 'never call getUserMedia on iOS' stronger.
- iOS: setSinkId IS SESSION-WIDE. WebKit's iOS speaker selection goes through AVAudioSessionCaptureDeviceManager::setPreferredSpeakerID, which sets one preferred speaker for the whole session. Calling cueEl.setSinkId(id) on an iPhone or iPad would move ALL of the page's audio, master included. Excluding iOS by UA sniff is therefore required for correctness, not just tidier UI. Remember iPadOS sends a Mac UA, so also check maxTouchPoints > 1.
- GROUPID REFUSAL IS TOO STRICT. The rule 'refuse dual mode if both resolve to the same groupId' conflicts with the researcher's own multi-endpoint USB interface strategy ('1/2' and '3/4' endpoints of one box usually share a container, so they share a groupId). Refuse only when the resolved deviceIds are identical: map 'default'/'communications' to the real endpoint by matching groupId and label. Only WARN when the groupIds match.
- WINDOWS 10 BLUETOOTH LABELS. Chrome lists both '... Stereo' and '... Hands-Free AG Audio' endpoints for a BT headset (audio_device_description.cc). Picking the Hands-Free one as the cue sink forces HFP mono at 8/16 kHz and silences the Stereo endpoint. Hide or flag labels containing 'Hands-Free'. Chrome also redacts AirPods names to just 'AirPods' (crbug 1163072), so two pairs of AirPods show identical labels. Add a per-device test tone and show groupId or position hints.
- SINK CHANGES CAUSE A DROPOUT. Changing an AudioContext sink suspends and resumes the context (spec event order: statechange suspended -> resolve -> sinkchange -> statechange running; see the WebKit PR 74675 description, matching Chrome). Pick the master sink before playback, or warn that switching mid-mix drops out briefly.
- USE ONE SIGNED LATENCY SLIDER. The offset can be needed in either direction: delay the cue when the BT speaker is slower, delay the master when the BT headphones are slower. Use one signed slider (for example -300 to +300 ms) that drives a DelayNode on whichever path is faster, with createDelay(maxDelayTime >= 0.3).
- SPLIT MODE: SIMPLIFY AND WARN. ChannelMergerNode inputs are already channelCount=1, 'explicit', with 'speakers' interpretation, so a stereo bus fed straight in is down-mixed to 0.5*(L+R). The extra mono GainNodes are optional. Practical caveats: Android/iOS 'Mono audio' accessibility settings, and phone audio effects such as Dolby Atmos, spatial audio or virtualizers, can collapse or cross-feed L/R and leak master into the cue ear. Tell users to turn these off.
- DO NOT RELY ON THE RECOVERY SPEC. For a media element whose sink disappears, the spec only says 'the user agent must take no action'. Do not count on a reroute. Detect the loss with devicechange plus re-enumeration, and fall back. https://w3c.github.io/mediacapture-output/
- CROSS-ORIGIN IFRAME NUANCE (Chrome). <audio>-based cue routing needs only allow="microphone" plus a mic grant, because HTMLMediaElement.setSinkId has no speaker-selection check. AudioContext.setSinkId needs allow="speaker-selection". Dual output in a preview iframe could therefore partly work in Chrome while failing in Safari and Firefox. Simplest rule stands: enable dual-device only top-level or same-origin.
- DATES THAT AFFECT ROLLOUT. Chrome M152 (which carries the desktop-Android setSinkId gating) went stable on 2026-08-25. Chrome milestones are now about 2 weeks apart (M153 stable 2026-09-08; M156 at stable cut in early October 2026). The original CL says Finch already enabled per-stream selection on 100% of desktop Android, so desktop-form-factor Android may have had <audio>.setSinkId before M152.
- NO SAFARI AudioContext.setSinkId SOON. Even if WebKit PR 74675 merges, the Apple-port AudioDestination::setSinkId is a no-op stub. Real routing is planned only for GStreamer (Linux ports). On Safari macOS, both outputs must therefore use the <audio>.setSinkId path, or the master must follow the OS default.
- REMOTE-CUE CAVEATS (unverified, design advice). For music over WebRTC, munge the SDP for Opus stereo=1 and a higher maxaveragebitrate, since the default is mono and voice-tuned. A QR-only exchange needs an offer AND an answer to pass between devices (two scans, cameras on both sides) unless there is a signaling server.
