- **unverifiable**: 6. For touch knobs, vertical drag (up = more) is preferred over circular rotation; ~200px full travel; touch-action:none + setPointerCapture; some phone UIs draw knobs as vertical bar sliders.

- **partly-true**: 7. touch-action is not inherited; at gesture start the browser intersects the values of the element and its ancestors up to the scroll container; changing it mid-gesture has no effect; pointercancel fires on browser pan/zoom takeover or too many pointers; every draggable control AND all its non-scrolling ancestors need touch-action:none or two-finger use can become a pinch; Baseline since Sept 2019.
  - CORRECTION: Correct: not inherited; changes after a gesture starts are ignored; pointercancel reasons include touch-action/pan-zoom takeover and 'too many simultaneous pointers'; Baseline 'widely available' since September 2019 (iOS Safari 13 added none, pan-x, pan-y and pinch-zoom). Two corrections. (a) Per the Pointer Events spec, the ancestor walk for PANNING stops at the nearest scroll container, but for ZOOMING it continues up to the document root. (b) How touch-action values combine across concurrent pointers (pinch) is 'out of scope' of the spec, so it is implementation-defined. Ancestors do not need none for a control's own touches, because intersection already takes the most restrictive value. The robust way to stop accidental pinch is touch-action:none on a full-viewport container (#app) so that touches in gaps between controls are covered, which the recommendation already does.
- **partly-true**: 8. iOS Safari ignores user-scalable=no and maximum-scale since iOS 10; pinch/double-tap zoom must be blocked with touch-action; iOS fires non-standard gesturestart/gesturechange and preventDefault on them is a common safeguard.
  - CORRECTION: Apple's Safari 10 notes say only: 'Pinch-to-zoom is always enabled for all users. The viewport setting for user-scalable is ignored.' maximum-scale is not mentioned there; in practice maximum-scale=1 still suppresses input-focus auto-zoom but not user pinch, so 'ignores maximum-scale' is an over-simplification. touch-action:none, pan-x, pan-y and pinch-zoom work on iOS only from Safari 13 (Sept 2019); manipulation works from 9.3. gesturestart is iOS-only (since iOS 2), non-standard, and absent from desktop Safari and Chrome Android.
- **partly-true**: 9. Pull-to-refresh/rubber-banding: set overscroll-behavior:none on BOTH html and body; one test found Chrome Android honours body and Safari 16 honours html.

## Extra findings
- TWO-OUTPUT REALITY ON PHONES (central to the user's request): the planned 'MASTER → [device] / HEADPHONES → [device]' pickers will not work on phones. iOS: no Web Audio output selection. Safari 18.4 added speaker selection 'on macOS' only, for HTMLMediaElement.setSinkId, with enumeration only after microphone permission (https://webkit.org/blog/16574/webkit-features-in-safari-18-4/). BCD's safari_ios 18.4 entry for HTMLMediaElement.setSinkId conflicts with WebKit's own post and looks wrong. AudioContext.setSinkId is unsupported in Safari and Firefox. Chrome Android: HTMLMediaElement.setSinkId is unsupported ('limitation in Android', crbug 41276355). AudioContext.setSinkId exists since Chrome 110, but Chromium's AudioManagerAndroid::GetAudioOutputDeviceNames returns only the default device unless UseAAudioPerStreamDeviceSelection() is true, which requires is_desktop() AND the kAAudioPerStreamDeviceSelection feature. So on Android phones there is effectively only 'default' (https://raw.githubusercontent.com/chromium/chromium/main/media/audio/android/audio_manager_android.cc). Dual output only works on desktop: Chrome/Edge 110+ via AudioContext.setSinkId, Firefox 116+ via media-element setSinkId and selectAudioOutput, macOS Safari 18.4+ via media element. On phones, the UX should say plainly that a Bluetooth speaker plus Bluetooth headphones is not possible, and offer master-only or split-mono through a wired Y-cable or USB DAC. Split-mono over a single Bluetooth device is pointless.
- TOUCH POINTERDOWN IS NOT A USER-ACTIVATION EVENT: per the HTML spec, activation-triggering events are keydown, mousedown, pointerdown only when pointerType is 'mouse', pointerup when pointerType is NOT 'mouse', and touchend (https://html.spec.whatwg.org/multipage/interaction.html#activation-triggering-input-event). Firing PLAY/CUE on pointerdown is fine for timing. But AudioContext.resume()/unlock, opening the file picker ('tap empty platter opens picker'), requestFullscreen, and probably the iOS switch-haptic label.click() must run from pointerup/click/touchend, or the first PLAY on touch may stay silent. Unlock audio on the first pointerup anywhere, e.g. the load tap or 'Try demo loops'.
- SONGS LIST CONTRADICTION: the recommendation says 'never put interactive controls inside a scroll container', yet places 48x48 [A]/[B] load buttons inside the pan-y scrolling list. List buttons must fire on click, not pointerdown, so that starting a scroll does not load a track; pointercancel will fire when the pan takes over.
- overscroll-behavior has no effect on scroll containers without scrollable overflow: partial in Safari (all versions) and Chrome until 144 per BCD. With html/body overflow:hidden it is likely a no-op on iOS, so touch-action:none on a full-viewport #app is the real protection.
- CROSSFADER UX: relative drag plus double-tap-to-centre is hostile to scratch cutting. Rapid double taps during cuts would reset the fader, and relative drag cannot do the 'touch the other end with a second finger to cut' technique the Cross DJ review praises in iOS apps (https://www.digitaldjtips.com/reviews/cross-dj-android/). Consider absolute (jump-to-finger) positioning when the 'cut' curve is on, and no double-tap reset on the crossfader.
- Mixxx alpha-beta coefficients are rate-dependent: alpha=1/8 and beta=alpha/32 are tuned for a 1 ms controller timer (kScratchTimerMs=1, kAlphaBetaDt=0.001), not per audio sample (https://raw.githubusercontent.com/mixxxdj/mixxx/main/src/controllers/scripting/legacy/controllerscriptinterfacelegacy.cpp; https://github.com/mixxxdj/mixxx/wiki/Midi-Scripting). Applied per sample at 48 kHz they would barely smooth anything, so run the filter per render quantum or ~1 kHz, or re-derive the coefficients.
- iOS silent/ringer switch: Web Audio follows the ringer switch unless navigator.audioSession.type = 'playback' is set (Safari/iOS 16.4+; not in Chrome) (https://bcd.developer.mozilla.org/bcd/api/v0/current/api.Navigator.audioSession.json). A DJ app should set it at startup or users will hear nothing with the phone on silent.
- Bluetooth latency: BT sinks add large, device-specific latency, so a cue on BT headphones and a master on a BT speaker would be offset from each other, and beatmatching by ear on BT headphones is unreliable. AudioContext.outputLatency exists in Chrome/Chrome Android 102+, Safari/iOS 18.4+ and Firefox 70+ (https://bcd.developer.mozilla.org/bcd/api/v0/current/api.AudioContext.outputLatency.json), but treat it as an estimate. Offer a manual 'headphone delay' trim if two outputs are ever possible (desktop).
- Wake Lock on iOS: Safari 16.4–18.3 is partial and 'Does not work in standalone Home Screen Web Apps' (bug 254545); it is fixed from 18.4 (https://bcd.developer.mozilla.org/bcd/api/v0/current/api.WakeLock.request.json). Safari 26 opens Home Screen sites as web apps by default, so standalone mode will be common.
- Fullscreen: iPhone has no element fullscreen. iPad has partial support (prefixed since 12, unprefixed 16.4) with a non-dismissable overlay button, and 'Swiping down exits fullscreen mode', which conflicts with platter and fader drags (https://bcd.developer.mozilla.org/bcd/api/v0/current/api.Element.requestFullscreen.json). Plain feature detection will offer it on iPad, so decide explicitly.
- Orientation lock: ScreenOrientation.lock is unsupported on iOS, available in Chrome Android since 38 (in practice requires fullscreen or an installed app) and in Firefox Android since 144 (2025-10-14) (https://bcd.developer.mozilla.org/bcd/api/v0/current/api.ScreenOrientation.lock.json). 'Never lock' is fine, but an optional landscape lock in Android fullscreen is possible.
- Output-device enumeration needs permission: other than the default devices, only devices with granted permission are listed, and output devices are additionally gated by the 'speaker-selection' permissions policy (https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/enumerateDevices). In the iframe preview, output pickers need allow='speaker-selection; microphone' or they will silently show only the default device.
- Hold-duration inconsistency: the spec uses 300ms (FX momentary), 350ms (needle lock), 450ms (fine mode), 600ms (load lock) and an unspecified Sync long-press. Consolidate to one or two values so users can learn them.
- Phone-portrait height budget: a 360x640 Android device can have about 500–570px of innerHeight depending on 3-button vs gesture nav and the URL bar. The fixed 264px DECKS page plus 44+120+72+52 of chrome may not fit. Compute sizes from the measured height rather than the 360x560 assumption.
- Unverified recommendation detail: I could not find 'Safari 26 tints its toolbar from CSS' (or the dropping of theme-color) in WebKit's Safari 26.0 feature post or the WWDC25 Safari 26 beta post. Treat it as unverified, and keep body background and theme-color anyway.
- Competitor patterns worth copying: djay 5.3 added 'New tools in crossfader bar with direct access to Neural Mix, FX, or Beat Jump', a crossfader-adjacent quick-tool strip. edjing added 'a focused-deck mode in portrait' (v9.1.4, Jul 2026) for single-deck focus on small screens.
