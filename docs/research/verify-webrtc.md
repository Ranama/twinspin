# verify-webrtc
- **partly-true**: 1. PeerJS 1.5.5 UMD build is byte-identical on jsDelivr/unpkg/cdnjs (HTTP 200, ACAO *, 86,948 bytes, SRI sha384-x0YgkOr/...dwczu); defines window.peerjs and deprecated window.Peer; npm main=dist/bundler.cjs, module=dist/bundler.mjs, neither usable from a CDN without a bundler.
  - CORRECTION: Everything checks out (all three URLs gave 200, ACAO *, 86,948 bytes and the same sha384 on 2026-10-06; 1.5.5 is still npm 'latest'). One part is overstated: dist/bundler.mjs imports bare specifiers ('peerjs-js-binarypack', 'webrtc-adapter', '@msgpack/msgpack'), so it cannot be loaded raw, but jsDelivr's https://cdn.jsdelivr.net/npm/peerjs@1.5.5/+esm (HTTP 200) or esm.sh rewrite the imports and serve it as an ES module with no bundler. Note also that the UMD bundle includes webrtc-adapter, which replaces global WebRTC constructors when it loads.
- **confirmed**: 2. PeerJS 1.5.5 defaults: host 0.peerjs.com, port 443, secure forced true for cloud host, key 'peerjs', path '/', pingInterval 5000; default iceServers = Google STUN + eu-0/us-0.turn.peerjs.com:3478 (peerjs/peerjsp); own config.iceServers replaces it; id regex /^[A-Za-z0-9]+(?:[ _-][A-Za-z0-9]+)*$/; global namespace under key 'peerjs'.
- **confirmed**: 3. peer.call requires a stream (host must be caller); answer(undefined,{sdpTransform}) gives receive-only; sdpTransform only rewrites LOCAL offer/answer, no remote hook; call.peerConnection exists synchronously after peer.call(); MediaConnection opens a data channel so 'close' fires on remote hangup (fixed in 1.5.0).
- **partly-true**: 4. Losing the signalling socket does not close live P2P connections; reconnect() re-registers the same id, throws on a destroyed peer, and emits errors if the id was taken; ICE 'failed' -> 'negotiation-failed' + close; 'disconnected' only logged; no ICE restart/renegotiation; peerjs-server defaults alive_timeout 60000, expire_timeout 5000, concurrent_limit 5000.
  - CORRECTION: The client-side behaviour is accurate, but the server default alive_timeout is 90000 ms, not 60000 (peerjs-server master src/config/index.ts and the published npm 'peer' 1.0.2). expire_timeout 5000 and concurrent_limit 5000 are correct. Two further details: (a) ICE 'disconnected' is logged and is also re-emitted to the app as MediaConnection event 'iceStateChanged'; (b) 'negotiation-failed' is emitted as an 'error' on the MediaConnection, not on the Peer. Edge case: if reconnect() reaches the server while it still holds the old client entry (same token, old socket not yet reaped), peer@1.0.2 attaches the new socket but sends no OPEN. The 'open' event then never fires, even though signalling works.
- **confirmed**: 5. 0.peerjs.com has no SLA; a maintainer said in 2022 there is no per-app limit; slow or failed registration keeps being reported: #461 (Sept 2024, ~20 s waits), #1350 (Oct 2025, open, multi-minute delays while status page green); older reports of hitting the 5000 limit; expect 10 s+ pairing.
- **partly-true**: 6. libwebrtc sender Opus encoder is configured from the REMOTE fmtp; Juberti said stereo=1 has no effect on setLocalDescription; parsed params stereo, maxaveragebitrate, ptime/minptime/maxptime, usedtx, cbr, useinbandfec, maxplaybackrate; default 32 kbps x channels; kVoip for mono, kAudio for stereo; frame lengths 10/20/40/60(/120); RFC 7587: sender MUST NOT send stereo when stereo=0/absent.
  - CORRECTION: The libwebrtc and RFC details are correct. Default 32 kbps x channels holds for maxplaybackrate above 16 kHz (12/20 kbps per channel for NB/WB). The RFC also says every receiver MUST be able to decode stereo. The Juberti attribution could not be verified. The statement is also misleading taken alone: stereo=1 in the LOCAL description does nothing for the local encoder, but it does decide whether the local DECODER outputs stereo (see claim 7). libwebrtc's own munging detector says Opus stereo munging is 'required to enabled stereo playout'. A TODO (issues.webrtc.org/376071290) plans to drive the mono/stereo application mode from track contentHint instead.
- **confirmed**: 7. libwebrtc Opus DECODER takes channel count from the receiver's own fmtp; without 'stereo' it decodes MONO unless field trial WebRTC-Audio-OpusDecodeStereoByDefault; so a Chrome/Safari listener must put stereo=1 in its LOCAL answer, which also makes the host encode stereo; doing it in the listener's PeerJS answer sdpTransform covers both ends.
- **partly-true**: 8. Chrome is tightening local SDP munging: M138 (PSA May 2025) makes removing an m= section an error; April 2025 PSA says modified ice-ufrag/ice-pwd will be rejected (no date); fmtp/FEC/DTX/codec-order changes are currently only DETECTED (metrics in webrtc-internals); stereo=1 munge works today but wrap it with fallback; remote munging is not restricted.
  - CORRECTION: The dates and facts are correct: the m= PSA was posted 2025-05-08 by Philipp Hancke for M138; the ufrag/pwd PSA was posted 2025-04-11 by Harald Alvestrand ('precise rollout dates have not yet been set'). One correction: other munging types are not merely 'detected until a future Chrome'. libwebrtc rejects any munging type listed in the Finch trial 'WebRTC-NoSdpMangleReject', so Google can start rejecting stereo munging (type 68) remotely without shipping a Chrome release. Some types are already rejected unconditionally (number of m= sections, SFrame, SCTP init, ice-options sped, cryptex, rtcp-xr rrtr). ufrag rejection is gated by trial 'WebRTC-NoSdpMangleUfrag'. Detection feeds UMA histograms (WebRTC.PeerConnection.SdpMunging.*) and log warnings; a webrtc-internals display was not verified. Munging checks apply only to setLocalDescription, so the remote description is unaffected.
- **refuted**: 9. setParameters shipped Chrome 68, Safari 11, Firefox 64; encodings[0].maxBitrate is a cap; the encoder target still comes from remote fmtp maxaveragebitrate (default 32 kbps/channel), so use both; raising maxBitrate alone does not lift a 32/64 kbps default target.
  - CORRECTION: The version numbers are right per MDN BCD (setParameters: Chrome 68, Firefox 64, Safari 11; the encodings.maxBitrate subfeature is listed as Chrome 69). The bitrate logic is wrong. In libwebrtc, an audio sender's encodings[0].maxBitrate goes through ComputeSendBitrate() and becomes send_codec_spec.target_bitrate_bps, capped only by b=AS and the codec max of 510 kbps, not by maxaveragebitrate. The encoder receives it via OnReceivedTargetAudioBitrate(), and UpdateAllowedBitrateRange() sets the BWE min and max both to that value. So setParameters({encodings:[{maxBitrate:192000}]}) on its own raises Opus from the 32/64 kbps default to about 192 kbps, subject to BWE. maxaveragebitrate munging is not needed for bitrate. Stereo still needs stereo=1 in the fmtp.
- **partly-true**: 10. RTCRtpReceiver.jitterBufferTarget (ms, 0-4000, else RangeError) shipped Chrome 124 (Apr 2024), Firefox 115 (Jul 2023), Safari 27.0 (released 2026-09-17, iOS 27); Safari 27 adds 'targetLatency'; libwebrtc treats it as a lower bound; leave unset for lowest latency; Chrome's playoutDelayHint superseded.
  - CORRECTION: The versions and semantics are correct. The date is wrong: Apple's Safari 27 release notes say 'Released September 14, 2026 - 27.0 (20625.1.29)', not 2026-09-17. BCD gives safari 27 with safari_ios mirrored, so iOS/iPadOS 27. The notes list 'targetLatency attribute in WebRTC (168225793)' and 'RTCRtpReceiver.jitterBufferTarget (173676035)' as separate items. Chrome still exposes playoutDelayHint (not removed).
- **unverifiable**: 11. Latency budget estimate: Opus 20 ms + ~6.5 ms look-ahead; Sept 2026 Android Wi-Fi RTT p50 41-72 ms/p99 94-119 ms; NetEq 40-120 ms; output 10-40 ms; ~100-250 ms to output; Bluetooth adds 100-300 ms (per-codec figures); remote ~0.2-0.5 s after touch and ~0.1-0.25 s behind local BT.
  - CORRECTION: Only the Opus figure checks out: the default algorithmic delay is about 26.5 ms (20 ms frame + 6.5 ms look-ahead). The 'Sept 2026 Android-to-Android test', the NetEq range and the per-codec Bluetooth numbers have no primary source and should be treated as rough guesses to be measured on the target devices. The app should measure end-to-end latency (inbound-rtp jitterBufferDelay/jitterBufferEmittedCount plus RTT/2) and let the user nudge the alignment by ear.
- **partly-true**: 12. Chrome needs a user gesture before AudioContext runs; MediaStream srcObject media elements were historically allowed to autoplay with a warning it may change; failed play() rejects NotAllowedError; iOS Safari autoplays MediaStream media only if the page is capturing or already playing audio, else play() must come from a user action; design one 'Tap to listen' and retry play() from a tap.
  - CORRECTION: Most of this is right. The AudioContext rule has applied since Chrome 71. NotAllowedError is correct. The iOS rule is WebKit's documented MediaStream policy (2017). The Chrome MediaStream autoplay exemption could not be found: current Blink AutoplayPolicy (autoplay_policy.cc, main) has no MediaStream special case. Chrome uses sticky document-level user activation (or MEI on desktop, or Home Screen install on mobile). So after the 'Tap to listen' tap, a later asynchronous play() in Chrome succeeds. On iOS the gesture is lost after awaits, so call audio.play() synchronously inside the tap handler to unlock the element (or start audio so 'page is already playing audio' applies), then set srcObject later.
- **partly-true**: 13. Play the remote stream via <audio playsinline autoplay>, not Web Audio: (1) Chrome bug crbug 121673 makes remote WebRTC in createMediaStreamSource silent unless attached to a media element; (2) iOS ignores element.volume; (3) iOS 15 extra-latency bug WebKit 230903 fixed Oct 2021 (r284689); (4) use getStats audioLevel for meter.
  - CORRECTION: Points 2-4 are correct. The bug number in point 1 is wrong: crbug 121673 (now issues.chromium.org/40184923) is a 2012 feature request, 'Hook up Web Audio API with WebRTC for audio processing', and is marked fixed. The silent-remote-stream bug is crbug 933677 (issues.chromium.org/40094084), 'MediaStream from RTC is silent (in WebAudio, MediaRecorder, etc.) if not attached to a media element'. It was filed 2019-02-20 and the tracker shows it still assigned (open). The workaround stands: if Web Audio is used on the listener, also attach the stream to a muted <audio> element.
- **partly-true**: 14. iOS Safari suspends WebRTC and Web Audio when the screen locks or Safari is backgrounded (Apple forum Feb 2025); Screen Wake Lock in Chrome/Chrome Android 84, Firefox 126, Safari 16.4; not in iOS standalone Home Screen apps until iOS 18.4 (WebKit 254545); navigator.audioSession.type='playback' Safari-only 16.4+ (Chrome none, Firefox preview), stops silent switch muting Web Audio.
  - CORRECTION: The wake lock and audioSession facts match BCD and WebKit. BCD safari_ios: 16.4-18.3 partial ('Does not work in standalone Home Screen Web Apps', bug 254545), full from 18.4. The specific Apple forum (Feb 2025) source for 'suspends WebRTC and Web Audio on lock/background' could not be checked. Keeping the screen on is still the safe design. Whether the silent switch is ignored follows from 'playback' mapping to iOS's playback audio category; this was not re-tested here.
## Extra findings
- CRITICAL: PeerJS's default TURN servers no longer resolve. On 2026-10-06, eu-0.turn.peerjs.com and us-0.turn.peerjs.com return NOERROR with no A/AAAA/CNAME records from both dns.google and cloudflare-dns.com (only an SOA for peerjs.com), and TCP 3478 to them fails. In practice the default PeerJS config is STUN-only. Source: https://dns.google/resolve?name=eu-0.turn.peerjs.com&type=A
- CRITICAL: The recommended static OpenRelay credentials (openrelayproject/openrelayproject) are no longer documented. https://www.metered.ca/tools/openrelay/ now says to 'sign-up for a free account and obtain your API Key' and fetch credentials from https://<app>.metered.live/api/v1/turn/credentials?apiKey=... (20 GB/month free). Static auth exists only via staticauth.openrelay.metered.ca with a shared secret for Nextcloud. Treat the proposed 4-URL ICE list as having no working TURN. Pairing will fail on Wi-Fi with client/AP isolation (guest or venue networks), across NATs, or when one device is on cellular. Expose TURN through TWINSPIN_CONFIG, for example a Metered API key or Cloudflare/Twilio TURN. Suggest a phone hotspot or home Wi-Fi as the supported setup, and show a clear 'devices can't reach each other' error after ICE 'failed'.
- Recommendation fix (bitrate): because libwebrtc applies setParameters encodings[0].maxBitrate as the Opus target (ComputeSendBitrate -> OnReceivedTargetAudioBitrate), drop maxaveragebitrate from the munge and set the bitrate with setParameters on the host. Keep the listener's local-answer munge to the bare minimum of 'stereo=1'. sprop-stereo=1 in a recvonly answer has no effect, because it is a sender-side parameter (RFC 7587 sec 7.1). usedtx=0 and cbr=0 are already the defaults, and Chrome's default Opus fmtp already contains 'minptime=10;useinbandfec=1'. The munging detector classifies the whole change as kAudioCodecsFmtpOpusStereo (68) as soon as stereo is added.
- Recommendation fix (setParameters): do NOT 'create encodings:[{}] if missing'. Per the WebRTC spec, changing the number of encodings in setParameters throws InvalidModificationError. Call getParameters() after negotiation, modify encodings[0] in place, and pass back the same object (transactionId). networkPriority only toggles DSCP marking in libwebrtc (config_.has_dscp), which Chrome applies only when DSCP is enabled on the PeerConnection, so expect no real effect.
- Recommendation improvement (munging fallback): Google can reject stereo munging remotely through the Finch trial 'WebRTC-NoSdpMangleReject' without shipping a new Chrome version (pc/sdp_munging_detector.cc). Besides the reactive 'webrtc' error -> {t:'recall'} path, run a local preflight before the first answer: create two RTCPeerConnections, add a recvonly audio transceiver, createOffer -> setRemote -> createAnswer, add stereo=1, then setLocalDescription. Fall back to an unmodified answer if that throws. setCodecPreferences cannot inject stereo=1: since M124 it only accepts codecs from RTCRtpReceiver.getCapabilities (discuss-webrtc PSA https://groups.google.com/g/discuss-webrtc/c/QS7y-7zR5ok). Munging is therefore the only route to stereo reception in Chrome and Safari.
- Recommendation fix (iOS autoplay): the 'Tap to listen' handler awaits PeerJS loading, signalling and ICE, so the user gesture has expired by the time the stream arrives. Inside the tap, synchronously call audio.play() on the <audio playsinline> element; WebKit lifts the gesture restriction on an element that was played during a gesture. Alternatively, start any audible or silent playback so the 'page is already playing audio' rule for MediaStream-backed media applies. Then set srcObject when the 'stream' event fires. Chrome uses sticky document activation, so a later play() succeeds there anyway.
- Recommendation fix (reconnect timing): peerjs-server's default alive_timeout is 90 s, not 60 s (the real 0.peerjs.com config is unknown). Reclaiming the same code after a crash can take about 90 s or longer when the old socket died without a close frame; if the socket closed cleanly the id is released immediately. Persisting the Peer 'token' option lets the same id re-attach immediately (peer@1.0.2 accepts the same id with the same token). In that path the server sends no OPEN, so 'open' never fires. Rather than depending on that, show 'Code taken, retrying' with a fallback to a new code.
- Recommendation detail: listen for MediaConnection 'iceStateChanged' (PeerJS emits it on every ICE state change, including 'disconnected') instead of polling. 'negotiation-failed' arrives as an 'error' on the MediaConnection, not on the Peer. peer.call() with a falsy stream returns undefined and emits no 'error', so guard against that.
- Security/privacy: ids share one global namespace on the public server (key 'peerjs'). A 4-character code over a 32-symbol alphabet gives about 1.05M combinations, and 'peer-unavailable' tells a scanner which codes are not in use, so anyone who guesses or sees the code can receive the DJ's audio. The host should accept one listener by default, show the connected listener, and offer 'kick' or 'new code'.
- Sandboxed iframe or preview hosting: the embedding page's CSP (connect-src) can block the PeerJS WebSocket to wss://0.peerjs.com:443, even if scripts from cdn.jsdelivr.net are allowed. ICE/RTP traffic is not governed by connect-src. Test the 'Second device' feature in the real preview; it may only work on the standalone HTTPS host.
- Library risk: PeerJS 1.5.5 (2025-06-07) is the latest stable release, with 2.0.0-beta.3 on the beta tag. No release has shipped in the 16 months since, and server-reliability issues (#1350) remain open. Loading the UMD bundle also runs webrtc-adapter, which replaces window.RTCPeerConnection and related globals. That is acceptable when it is lazy-loaded, but it should not run before the core DJ engine has initialised if the engine itself uses WebRTC objects.
- Listener engine note: Firefox's default Opus fmtp has historically included 'stereo=1' (stated from memory, not re-verified), so a Firefox listener may get stereo with no munging. Chrome and Safari need the local stereo=1 munge (libwebrtc audio_decoder_opus.cc).
- Two clarifications: (1) The Opus application mode follows the channel count: mono -> kVoip, stereo -> kAudio (music). Without stereo=1 the host's encoder runs in speech-tuned mono, which is a strong reason to keep the stereo munge even at higher bitrates. (2) jitterBufferTarget in Chrome and libwebrtc maps to SetJitterBufferMinimumDelay, so a 'Stable' preset of 80-150 ms raises the floor; it does not reduce latency.
